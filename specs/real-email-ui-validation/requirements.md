# 真实邮箱 UI 验证需求

> 状态：待确认
> 日期：2026-08-19
> 范围：Windows Tauri 桌面端、QQ 邮箱真实采集、完整 UI 流程
> 安全级别：真实邮箱、真实授权码、真实发票数据

## 1. 固定测试参数

| 参数 | 值 |
|---|---|
| 测试邮箱 | `879***187@qq.com`（完整地址仅保存在本机测试配置中） |
| 授权码来源 | 仓库根目录 `.env.local` 的 `INVOICE_IMAP_PASSWORD` |
| 邮件时间范围 | `[2026-06-01, 2026-07-01)`，完整覆盖 2026-06-01 至 2026-06-30 |
| 用户常驻城市 | 北京 |
| 邮箱访问模式 | 严格只读，不改变邮件、文件夹或任何邮件标记 |

`.env.local` 已由 `.gitignore` 忽略。测试工具只能在受控进程中加载允许的变量，不得打印、复制、上传或写入前端资源。

## 2. 目标

1. 使用真实 QQ 邮箱验证登录、检索、附件提取、解析、去重、归组、审核和输出。
2. 使用真实 Windows Tauri UI 验证首次设置、批次运行、错误处理、中断恢复和完成结果。
3. 保证测试前后邮箱内容和标记完全不变。
4. 保证授权码不进入数据库、日志、截图、终端报告、WebDriver 参数或 Git。
5. 将真实测试与普通 CI 隔离，只有人工显式启用时才能运行。
6. 形成可重复的开发迭代和发布门禁。

## 3. 用户故事

### US-1：真实邮箱采集

作为测试人员，我希望应用读取 2026 年 6 月的真实邮箱附件，以验证产品在真实邮件格式下可以工作。

### US-2：邮箱保持只读

作为邮箱所有者，我希望测试不会设置已读、移动、删除、复制、标记或发送任何邮件，以保证生产邮箱状态不受影响。

### US-3：真实 UI 操作

作为产品验收人员，我希望通过 Windows 桌面 UI 完成从设置到输出的流程，而不是只验证后端函数。

### US-4：秘密不泄露

作为授权码所有者，我希望授权码只存在于受控进程内存中，不出现在任何可长期保存的测试制品里。

### US-5：北京归组

作为常驻北京的用户，我希望北京出发、返回北京和北京本地消费能够按产品规则正确归组。

## 4. 功能与安全需求

### R1：授权码加载

- 当真实测试启动时，测试启动器应只从仓库根目录 `.env.local` 加载允许列表中的 `INVOICE_IMAP_PASSWORD`。
- 当变量缺失、为空或形状明显错误时，测试启动器应在启动应用前失败。
- 当测试启动器输出日志时，不得输出授权码、授权码长度、授权码哈希或包含授权码的命令行。
- 当测试结束时，父进程应清除临时环境变量并终止所有子进程。

### R2：IMAP 严格只读

- 当应用打开邮箱文件夹时，IMAP 客户端应使用只读邮箱命令，而不是读写选择命令。
- 当应用抓取邮件正文时，应使用不会设置 `\\Seen` 的 PEEK 语义。
- 在真实测试路径中，系统不得执行 `STORE`、`COPY`、`MOVE`、`APPEND`、`DELETE`、`EXPUNGE` 或等价写操作。
- 当测试开始和结束时，系统应记录受测 UID 的只读指纹并比较 UID、FLAGS、大小和 Message-ID。
- 如果任一邮件标记或邮箱指纹发生变化，真实测试应判定失败并停止后续测试。

### R3：日期范围

- 当用户选择 2026-06-01 至 2026-06-30 时，系统应向 IMAP 发送 `[2026-06-01, 2026-07-01)` 的检索范围。
- 系统不得扫描该范围外的邮件正文。

### R4：本地测试隔离

- 当真实 UI 测试启动时，系统应为本次运行创建唯一的仓库外数据目录。
- 应用数据库、日志、原件、解析文件和输出只能写入该目录。
- 测试不得向仓库 `fixtures/`、源码目录或用户正式应用数据目录写入真实邮件附件。
- 测试结束后应先完成安全审计，再由用户确认是否删除隔离目录。

### R5：MVP 会话凭据

- 当用户在 UI 输入授权码时，授权码应只保存在 Rust 后端会话内存中。
- 前端提交后应清空密码字段，不写入浏览器持久化存储。
- 当应用退出或用户断开邮箱时，会话凭据应失效。
- 应用重启后应重新要求授权码。
- 文件夹导入不得依赖邮箱凭据或 Keychain。

### R6：首次设置 UI

- 当首次启动应用时，系统不应要求注册或登录产品账号。
- 用户应能配置测试邮箱、常驻城市北京和数据来源。
- 当邮箱连接尚未测试成功时，完成页不得显示“全部准备就绪”。
- 当邮箱字段变化时，之前的连接成功状态应立即失效。

### R7：流水线状态

- 当用户启动批次时，前端应在后台任务开始前完成事件订阅。
- 当账号、授权码或前置配置失败时，UI 应在 1 秒内进入可操作的失败状态。
- 后台任务应有唯一 `pipeline_id`、持久化状态和唯一终态。
- 当应用关闭后重新启动时，系统应能恢复未完成批次。

### R8：真实采集与解析

- 当真实邮箱存在附件时，系统应在隔离目录提取并按格式分类。
- 系统应记录扫描邮件数、附件数、识别为发票数、解析成功数、失败数和重复数。
- 报告不得包含完整邮件主题、正文、邮箱授权码、完整发票号、税号或金额明细。
- 同一附件重复出现时，应通过 Message-ID、内容哈希和发票号策略收敛。

### R9：北京归组

- 当设置中的常驻城市是北京时，流水线应从设置读取该值并传给归组引擎。
- 生产流水线不得硬编码北京。
- 当单元测试把常驻城市改为其他城市时，归组结果应随配置变化，用以证明配置链路真实生效。
- 真实 UI 审核应允许人工确认北京本地消费与北京出发/返回行程。

### R10：人工审核

- 当关键字段、重复或归组存在歧义时，批次应进入待审核状态，不得自动通过。
- 用户应能在同一工作区查看行程、发票列表、原件和字段。
- 未解决阻断问题时不得生成最终输出。

### R11：输出验证

- 系统应在隔离目录生成预期输出，并验证文件存在、非空、可打开。
- Excel/CSV/PDF 的张数和总计应与审核确认结果一致。
- 单个输出失败时应允许单独重试。
- 第一轮真实邮箱验收不向 Concur 或任何外部地址发送邮件。

### R12：自动化分层

- 普通 CI 应运行不需要真实凭据的单元、集成和模拟 UI 测试。
- 真实邮箱后端测试应保持默认忽略，并要求显式开关。
- 真实 UI 自动化不得把授权码输入 WebDriver 命令或保存截图。
- 授权码输入控件由模拟 UI 测试和一次人工真实冒烟测试覆盖；真实全流程自动化使用后端创建的临时凭据会话。

## 5. 非目标

- 不删除、移动、标记、回复或转发测试邮箱中的邮件。
- 第一阶段不发送 Concur 收据邮件。
- 不把真实发票复制到仓库测试夹具。
- 不把真实金额和发票号码写入 Git 可跟踪的基线文件。
- 不使用真实测试替代合成数据单元测试。
- 不在本轮建设用户账号、云同步和长期凭据加密。

## 6. 总体验收门禁

只有同时满足以下条件，才可以把真实 UI 验证标记为通过：

1. 邮箱前后只读指纹完全一致。
2. `.env.local` 和授权码未出现在 Git、日志、截图和测试报告中。
3. UI 不存在 0% 假死，所有任务都有明确终态。
4. 2026 年 6 月范围外邮件未被抓取正文。
5. 数据只写入本次隔离目录。
6. 北京配置真实进入归组引擎。
7. 需要审核的项目未被自动通过。
8. 输出文件数量、发票数量和金额总计经过人工确认。
9. Windows UI、Rust 测试和前端检查均通过。
