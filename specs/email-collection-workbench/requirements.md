# 独立邮件收集工作台需求

## 1. 背景与结论

当前实现把邮件搜索、附件下载、发票解析、去重、归组和批次写入放在同一条流水线中。该模式使“来源材料是否完整”和“报销数据是否正确”两个不同问题相互影响，也使失败恢复依赖多个阶段检查点同时一致。

产品应拆分为两个独立生命周期：

1. **邮件收集任务**：发现邮件、形成逐封台账、下载并保存附件、完成来源审核和人工补充。
2. **报销批次**：由用户选择已经收集的材料或本地文件，随后执行解析、发票判断、去重、费用生成和归组。

该拆分符合用户心智：先确认“材料是否收齐”，再处理“如何报销”。

## 2. 产品边界

### 2.1 邮件收集任务负责

- 用户创建一次性、日期有界的邮件收集任务。
- 只读搜索邮箱并为每封邮件建立台账。
- 下载具名附件，安全展开 ZIP，并保存可供后续使用的原始文件。
- 对邮件和附件做来源级分类，不做发票字段解析。
- 保留同一邮件下发票候选、行程单候选、消费明细和其他附件的关联。
- 对链接交付、通知型、下载失败和不支持文件提供用户审核入口。
- 允许用户把手工下载的本地文件补充到指定邮件材料包。
- 显示材料是否已经被某个报销批次引用。

### 2.2 邮件收集任务不负责

- 不提取票号、金额、日期、销售方等发票字段。
- 不判定最终有效发票或无效票据。
- 不执行发票业务去重，不计算报销金额。
- 不创建费用记录，不执行行程归组。
- 不导出 Excel，不上传 Concur。

### 2.3 报销批次负责

- 新建批次只填写批次名称，创建时间由系统生成。
- 用户进入空批次后选择“从邮件收集任务导入”或“导入本地文件”。
- 用户从收集任务中选择整封邮件材料包或具体附件。
- 用户确认导入后，系统才执行解析、有效性判断、去重、费用生成和归组。
- 批次始终保留到收集任务、邮件和原附件的来源关系。
- 批次审核完成后才提供 Excel 导出或 Concur 上传。

## 3. 用户故事

1. 作为报销用户，我希望先独立检查一个日期范围内的邮件是否收集完整，避免解析失败被误认为没有邮件或没有附件。
2. 作为报销用户，我希望在同一封邮件下看到全部附件并补充手工下载文件，以免发票与行程单失去关系。
3. 作为报销用户，我希望创建批次时选择已经审核过的邮件材料，再开始发票解析和归组。
4. 作为审核用户，我希望知道某份收集材料是否已用于其他批次，避免重复报销。
5. 作为用户，我希望邮件收集失败可以独立重试，不影响已经存在的报销批次。

## 4. 验收条件

### R1 独立任务创建

- 当用户进入“邮件收集”主导航时，系统应显示收集任务列表，而不是要求先选择报销批次。
- 当用户新建收集任务时，系统应要求填写任务名称和日期范围，并明确显示当前会话邮箱；MVP 固定读取 INBOX。
- 当收集任务创建时，系统不得创建报销批次。
- 当用户创建报销批次时，系统不得要求填写邮箱、日期范围或发票来源。

### R2 来源级收集

- 当任务搜索到邮件时，系统应为每个 UID 记录一条邮件台账终态。
- 当邮件包含多个附件或 ZIP 展开文件时，系统应将所有逻辑附件保留在同一邮件材料包下。
- 当附件通过类型、大小和安全校验时，系统应保存原始文件供后续批次导入。
- 收集阶段的附件状态应使用“待解析文件”“配套材料候选”“已过滤”“不支持”“下载失败”等来源级表述，不得显示“有效发票”或解析金额。
- 收集任务不得调用发票字段解析、业务去重或归组模块。

### R3 用户审核和补充

- 当邮件仅提供下载链接时，系统应标记“需手工下载”，且不得自动访问正文链接。
- 当邮件疑似为开票通知但没有可取得文件时，系统应标记“需确认”。
- 当用户选择“下载后补充文件”时，新增文件应关联到当前邮件材料包，不得成为无来源孤立文件。
- 当用户确认邮件无关时，系统应保留忽略状态、操作时间和原始收集结论。
- 当待确认、下载失败或需手工下载邮件尚未处置时，收集任务应显示“审核未完成”。

### R4 批次选择导入

- 当用户进入空批次时，系统应提供“从邮件收集任务导入”和“导入本地文件”两个明确入口。
- 当用户选择邮件来源时，系统应先选择收集任务，再选择邮件材料包或附件，最后确认导入范围。
- 当用户确认导入时，系统应创建不可变导入快照并保留收集任务、邮件、附件来源 ID。
- 只有导入快照建立后，系统才应开始解析、有效性判断、去重、费用生成和归组。
- 当同一邮件包含多个附件时，批次解析后仍应保留这些附件来自同一材料包的关系。

### R5 重复使用提示

- 当附件已经被其他批次引用时，批次选择器应默认不选中，并显示首次使用批次。
- 当用户明确再次选择该附件时，系统应给出重复使用警告；最终是否计入金额仍由批次内发票去重规则决定。
- 删除草稿批次时，不得删除收集任务及其原始附件。

### R6 独立恢复

- 当邮件收集任务失败时，用户应能在邮件收集工作台重试该任务，而不进入批次页面。
- 当批次解析失败时，收集任务及其已下载附件不得被修改。
- 两类任务应使用不同的状态机和检查点命名空间，避免收集检查点污染解析恢复状态。

### R7 隐私、只读和存储

- 邮箱读取应继续使用只读命令、`BODY.PEEK` 和读取前后 FLAGS 指纹核对。
- 系统不得持久化邮件正文、正文链接或邮箱授权码。
- 已下载候选附件应进入受控的本地材料库，使用内容哈希去重并接受磁盘配额管理。
- 清理收集任务前，系统应提示其被哪些批次引用；被引用文件不得静默删除。

### R8 历史兼容

- 现有批次及其发票、费用、归组和附件不得因升级被改变。
- 对已经存在的批次内邮件台账，系统应迁移为“历史收集任务”并建立对应批次来源引用，或明确标记为旧版来源记录。
- 迁移不得伪造未记录的邮件或附件。

### R9 邮件台账列表与分组

- 收集任务详情应使用全宽邮件表格，不得使用邮件队列与材料包左右常驻对照布局。
- 邮件表格字段固定为：收件时间、主题、发件人、附件数、处理结果、状态、操作。
- 收件时间在表格和审核页只显示日期部分，格式为 `YYYY-MM-DD`；默认按收件日期倒序，缺失日期排在最后。
- 邮件必须互斥归入“需要用户处理”“待审核”“已审核”三个分组，并显示各组数量。
- “需要用户处理”包含需手工下载、需确认和处理失败且尚未处置的邮件；“待审核”包含其余未处置邮件；已处置邮件归入“已审核”。
- 列表应分页显示，点击行或操作按钮进入独立审核页，返回后保留原分组、页码和排序状态。

### R10 独立邮件审核页

- 审核页应显示主题、发件人、收件日期、处理结果、当前状态和邮件正文纯文本。
- 正文只在用户进入审核页时通过 `BODY.PEEK` 按需读取，不得持久化；读取前后必须核对 FLAGS 不变。
- 系统不得渲染邮件 HTML、远程图片、脚本或跟踪资源，只显示清理后的纯文本。
- 邮件中的发票下载相关 HTTPS 链接应整理为安全链接清单，只显示操作名称和站点域名，不在日志或本地数据库保存完整 URL。
- 用户确认后，链接应通过后端校验并使用 Windows 系统浏览器打开；非 HTTPS、带凭据、越界或已变化的链接必须拒绝。
- 正文读取失败不得阻止用户查看已保存的邮件元数据、附件和执行人工处置。

### R11 附件审核与补充

- 审核页应列出同一邮件的全部附件并保留配套关系，显示文件名、类型、大小、来源级状态和是否已被批次使用。
- PDF、OFD、XML 和图片附件应按需预览；预览失败时应提供“用系统程序打开”，不得占据页面常驻主区域。
- 用户可把通过浏览器下载的本地文件补充到当前邮件材料包；补充成功后该邮件自动进入“已审核”。
- 用户可明确执行“材料已齐全”“确认无关”或“重新打开”，所有操作沿用现有处置留痕。

## 5. UI 信息架构要求

### 5.1 主导航

1. `01 邮件收集`
2. `02 报销批次`
3. `03 设置与数据`

### 5.2 邮件收集任务列表

- 顶部主操作：“新建收集任务”。
- 汇总：运行中、待审核、审核完成、失败。
- 列表字段：任务名称、邮箱掩码、日期范围、扫描邮件数、待操作数、可导入文件数、任务状态、更新时间。
- 行操作：查看、继续审核、重试；删除放入次级菜单并执行引用检查。

### 5.3 收集任务详情

- 页头：任务名称、邮箱掩码、日期范围、只读状态、运行/审核状态。
- 汇总条：全部邮件、带附件、需手工下载、需确认、非发票相关、失败。
- 主工作区：全宽邮件表格，按“需要用户处理 / 待审核 / 已审核”分组。
- 表格字段：收件日期、主题、发件人、附件数、处理结果、状态、操作；默认按日期倒序并分页。
- 附件只显示来源级状态、类型、大小、下载结果和批次使用情况。
- 点击邮件进入独立审核页；审核页显示安全正文、下载链接、同邮件附件及补充/处置操作。
- 操作：打开下载链接、下载后补充、确认无关、重新打开、重试失败邮件、完成来源审核。
- 不显示金额、票号、费用类型、行程归组或 Concur 字段。

### 5.4 批次导入选择器

- 第一步：选择一个已完成或可用的收集任务；同一批次可分多次导入不同任务。
- 第二步：按邮件材料包选择；默认包含可用候选文件和同邮件配套材料。
- 第三步：显示文件数、已在其他批次使用数、待确认邮件数和导入风险，用户确认后开始解析。
- 解析完成后进入现有“费用清单”和“归组”视图。
- 批次中不再展示完整邮件处理台账，只展示来源引用和返回收集任务的入口。

## 6. MVP 约束

- 收集任务是用户主动创建的一次性任务，不做后台定时监控。
- MVP 只读取 INBOX。
- 不自动访问正文下载链接。
- 不在收集阶段运行 OCR、PDF/OFD/XML 发票字段解析。
- 不在收集工作台提供 Excel 或 Concur 操作。

## 7. 待用户确认的产品决策

1. 同一收集任务是否允许导入多个批次。建议允许，但对已使用材料默认不选中并强提醒。
2. 收集任务完成审核后是否允许继续补充文件。建议允许重新打开审核，所有补充动作留痕。
3. 收集附件的默认保留策略。建议 MVP 不自动删除，由用户在“设置与数据”中执行受控清理。
