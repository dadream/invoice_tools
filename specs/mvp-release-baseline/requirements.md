# Invoice Assistant MVP 发布需求基线

> 状态：已由产品负责人确认产品决策；2026-08-26 已确认D21–D22范围变更，待更新任务计划确认后实施
> 版本：1.4
> 日期：2026-08-26
> 决策来源：`specs/mvp-release-baseline/decision-record.md`（原D01–D18、2026-08-25新增D19–D20及2026-08-26新增D21–D22）
> 适用范围：Windows 11 x64 免安装 Alpha、Beta 和正式版

## 1. 产品定义

Invoice Assistant 是面向中国大陆 Concur 差旅报销个人用户的 Windows 本地工具。产品将邮箱或本地文件中的发票转换为经过解析、校验、去重、归组和人工审核的报销批次；整理完成后，用户可创建Concur报销单草稿、创建并填写费用、上传且关联对应发票。软件生成未提交草稿，企业规则调整和最终提交由用户在Concur中完成。

首版采用 Concur 核心定位，同时保留纯本地模式。纯本地模式不是降级产品：除 Concur 发送外，它拥有相同的解析、归组、审核和输出能力。

## 2. 发布阶段

1. **内部 Alpha**：5 名用户，每人至少 3 个真实历史批次；允许候选包未签名，但必须标记为内部测试版并说明 Windows 警告。
2. **小范围 Beta**：30–50 名用户；必须使用可信代码签名，完成真实邮箱、免安装、备份迁移、Concur草稿上传和收据邮件兼容路径验证。
3. **正式版**：满足本文件全部发布门禁，P0/P1 缺陷为零，法律、支持和发布材料完整。

## 3. 已确认范围

### 3.1 MVP 包含

- Windows 11 x64 免安装 ZIP，系统 WebView2 Evergreen Runtime。
- 本地单用户，无注册、登录、余额、充值、订阅和自动计费。
- 只读邮箱导入，以及本地发票/配套票据单文件、多文件和文件夹导入；本地UI不提供`.eml`入口。
- XML、OFD、PDF 和图片；图片低置信时强制人工补录。
- 采集、解析、校验、去重、归组、人工审核、输出完整流程。
- 批次内部只有费用清单和归组两个一级视图；完成审核后冻结快照，再独立选择导出Excel或上传Concur。
- 以版本化本地费用项维护稳定业务字段；目标系统字段仅在上传阶段通过配置映射生成。
- 中国大陆、简体中文、人民币；境外和多币种允许导入但必须人工确认，不承诺自动处理准确率。
- 确定性规则归组；规则不能确定时进入人工审核，不调用外部大模型。
- Excel、CSV、打印合订本、标准目录和原件输出。
- 用户确认后创建Concur报销单草稿、创建并填写费用、上传且关联对应发票、回读核对；最终状态保持未提交。
- 公开 Beta/正式版的 Concur 邮件试发、用户确认和防重复批量发送。
- 显式未加密备份包导出/导入，包含完整性校验和隐私警告，但不宣称验证了同一产品用户。
- 手动检查更新、用户主动删除本地数据、脱敏诊断和发布证据。

### 3.2 MVP 不包含

- 产品账号、登录、MFA、余额、订阅和支付。
- 邮箱授权码或 OAuth Token 持久化。
- 应用层数据库加密、账号匹配加密备份、云同步和严格同用户身份验证。
- 外部 LLM、云 OCR、自动遥测或后台自动更新。
- Concur 最终提交、审批、付款、公司报销限额和核准金额处理。
- 无人值守、后台隐藏、保存Concur登录凭据或绕过用户确认的自动化。
- 未经目标租户探测和真实验证的跨公司通用Concur适配承诺。
- Windows 服务、驱动、开机启动、文件关联、静默安装或提权。
- macOS、Linux 和 Windows ARM64 正式支持。
- 对 Windows 10 普通版作正式支持承诺；Windows 10 ESU/LTSC 仅尽力兼容。

## 4. 用户故事

1. 作为不能安装软件的员工，我希望解压 ZIP 后直接运行，不请求管理员权限。
2. 作为差旅报销用户，我希望从邮箱或本地文件收集当月发票并保持邮箱完全不变。
3. 作为重视隐私的用户，我希望授权码不落盘，且产品不把发票或行程数据发送给外部大模型。
4. 作为报销人，我希望系统自动完成可确定的解析和归组，把不确定项交给我审核而不是猜测。
5. 作为使用 Concur 的用户，我希望发票整理完成后，软件为我创建未提交报销单草稿、填写费用并关联正确发票，让我只需在Concur中检查公司规则并最终提交。
6. 作为数据所有者，我希望可以导出备份并在另一台电脑导入，同时清楚知道 MVP 备份未加密且不验证用户身份。
7. 作为受管电脑用户，我希望能把发布者、哈希、联网范围和权限说明交给 IT 审核。
8. 作为测试和发布负责人，我希望每项需求都有任务、用例和证据，发布结论可复核。
9. 作为报销人，我希望主发票、行程单和消费明细作为一个发票单管理，不会被重复计成多笔费用。
10. 作为报销人，我希望系统先建立有明确依据的行程组，再建议其他发票归入；没有证据时不要猜测行程。
11. 作为报销人，我希望疑似重复默认不进入申报总额，只有我明确确认不是重复后才计入。
12. 作为报销人，我希望在软件中核对的是稳定、易懂的费用信息；更换公司或Concur配置时不需要重新修改已经审核的费用数据。

## 5. 功能需求与验收条件

### R01 无账号本地使用

WHEN 用户首次启动 MVP，THE SYSTEM SHALL 直接进入本机准备和业务设置流程，不要求注册、登录、余额或订阅。

WHEN 用户选择纯本地模式，THE SYSTEM SHALL 在没有产品服务器和产品账号的情况下完成导入、处理、审核和输出。

### R02 双模式定位

WHEN 用户选择使用模式，THE SYSTEM SHALL 提供“Concur 草稿上传”和“纯本地输出”两个入口，并准确说明二者差异；收据邮件是Concur模式的兼容降级路径。

IF Concur 不可用或被企业策略阻止，THEN THE SYSTEM SHALL 允许用户切换纯本地模式且不丢失已处理结果。

### R03 本地文件来源

WHEN 用户选择单个/多个发票或配套票据文件，或选择包含这些票据的文件夹，THE SYSTEM SHALL 支持从本机读取 XML、OFD、PDF 和图片，并在处理前列出主发票、已挂载材料、待挂载材料、疑似重复、跳过和不支持的文件。

THE LOCAL IMPORT UI SHALL NOT 提供`.eml`选择、拖放或正式支持文案；邮件/EML解析器仅可作为只读邮箱采集内部实现或历史兼容能力。

IF 文件损坏、加密、过大或格式不支持，THEN THE SYSTEM SHALL 隔离该文件、保留其他结果并给出可执行原因。

### R04 邮箱正式支持边界

WHILE 处于 Alpha，THE SYSTEM SHALL 对 QQ 邮箱完成真实只读验证，其他标准 IMAP 服务标记为实验性。

BEFORE 公开 Beta，THE TEST SUITE SHALL 完成 QQ 和 163 的正式兼容验证；Gmail、Outlook/Office365 未完成真实验证前不得在产品文案中标记为正式支持。

### R05 不调用外部大模型

WHEN 系统进行邮件识别、归组或费用类型建议，THE SYSTEM SHALL 使用本地规则和用户配置，不向外部 LLM 发送邮件、发票、行程或用户字段。

IF 本地规则不能确定结果，THEN THE SYSTEM SHALL 将项目标记为待审核，而不是静默猜测。

### R06 地区、语言和币种

WHEN 处理中国大陆人民币票据，THE SYSTEM SHALL 使用简体中文和人民币精确小数进行展示、校验和汇总。

IF 票据涉及境外城市、外币或无法识别的税制，THEN THE SYSTEM SHALL 保留原值并要求人工确认，不自动折算汇率。

### R07 首次启动

WHEN 用户首次运行，THE SYSTEM SHALL 先检查 WebView2、数据目录和隐私状态，再进入报销资料和来源设置。

WHEN 正常环境检查通过，THE SYSTEM SHALL 自动前进，避免把技术术语和无关选择暴露给用户。

### R08 会话凭据

WHEN 用户提交邮箱授权码，THE SYSTEM SHALL 只在 Rust 后端当前进程内存保存，并立即清空前端输入值。

WHEN 用户断开邮箱或应用退出，THE SYSTEM SHALL 使会话凭据失效。

THE SYSTEM SHALL NOT 将授权码写入 SQLite、配置、日志、崩溃报告、命令行、截图、测试报告或前端持久化存储。

### R09 邮箱严格只读

WHEN 应用访问邮箱文件夹，THE SYSTEM SHALL 使用只读选择和不会设置 `\\Seen` 的读取语义。

THE SYSTEM SHALL NOT 执行改变邮件、旗标、文件夹或服务器状态的 IMAP 操作。

IF 测试前后 UID、FLAGS、大小或 Message-ID 指纹变化，THEN THE TEST SUITE SHALL 判定失败并停止发布验证。

### R10 日期范围

WHEN 用户选择自然月，THE SYSTEM SHALL 使用包含开始日、不包含下一月第一日的半开区间查询邮件。

WHEN 测试使用 2026 年 6 月，THE SYSTEM SHALL 仅抓取 `[2026-06-01, 2026-07-01)` 范围内的邮件正文和附件。

### R11 可恢复流水线

WHEN 用户启动批次，THE SYSTEM SHALL 为批次生成唯一 `pipeline_id`，在任务开始前完成事件订阅，并持久化每个安全阶段的检查点。

IF 应用关闭、任务失败或系统重启，THEN THE SYSTEM SHALL 恢复到最近安全点，或明确说明为什么只能安全回退。

### R12 解析与置信度

WHEN 输入包含结构化 XML/OFD 或文本 PDF，THE SYSTEM SHALL 优先读取结构化字段，不调用 OCR。

WHEN 输入是图片或扫描件，THE SYSTEM SHALL 使用随应用分发的本地 OCR；不得要求用户另装 Python 或开发环境。

IF 金额、号码、日期或税额低于置信门槛，THEN THE SYSTEM SHALL 阻止自动通过并进入人工补录。

### R13 校验与去重

WHEN 发票完成解析，THE SYSTEM SHALL 校验日期、金额、税额、税率、抬头和税号等适用规则，并记录可解释结果。

WHEN 同一邮件、附件或发票重复出现，THE SYSTEM SHALL 使用 Message-ID、内容哈希和发票标识收敛，不静默删除原始证据。

WHEN 同批次或跨批次发现疑似重复，THE SYSTEM SHALL 立即把重复候选标记为“不计入申报总额/不创建Concur费用”，展示依据并保留原始证据。

IF 用户暂不决定或确认重复，THEN THE SYSTEM SHALL 继续保持不计入；ONLY WHEN 用户明确选择“不是重复，计入总额”，THE SYSTEM SHALL 才把该发票单恢复为计入状态并记录审计事件。

### R14 本地行程归组

WHEN 用户设置一个或多个常驻城市，THE SYSTEM SHALL 把该配置传入本地归组引擎，不硬编码北京。

WHEN 存在铁路/航空城际票据或已挂载行程单等强证据，THE SYSTEM SHALL 先建立包含锚点、起止日期和城市链的明确候选行程组。

AFTER 明确行程组建立，THE SYSTEM SHALL 再根据日期、城市和票种判断酒店、餐饮、出租车等其他发票单是否建议归入该组，并保存依据。

IF 不存在明确行程锚点，THEN THE SYSTEM SHALL NOT 自动建立差旅行程；相关发票保持待归组或进入明确的市内消费集合。

IF 规则存在歧义或冲突，THEN THE SYSTEM SHALL 进入人工审核，不调用外部模型。

### R15 人工审核

WHEN 本地费用字段、票面事实、重复、规则或归组存在问题，THE SYSTEM SHALL 进入审核工作区，允许查看行程、`ExpenseItem`、发票单、主发票、配套材料和字段来源；该工作区不得因目标Concur租户不同而改变字段集合。

WHEN 存在未解决阻断项或金额合计不一致，THE SYSTEM SHALL 禁止完成审核；没有有效 `ReviewSnapshot` 时禁止生成新的最终输出和 Concur 上传/发送。

WHEN 用户移动、排除或编辑发票，THE SYSTEM SHALL 提供键盘等价操作和撤销能力。

### R16 输出

WHEN 用户在有效审核快照的独立交付选择中选择“导出Excel”，THE SYSTEM SHALL 依据该快照和稳定本地费用字段生成Excel；标准目录、CSV、打印合订本和原件集合如保留，必须使用同一快照且不依赖Concur映射是否完整。

THE SYSTEM SHALL 使用精确小数保证 UI、Excel、CSV 和 PDF 的张数及金额合计完全一致。

IF 单个输出失败，THEN THE SYSTEM SHALL 允许只重试失败项，不要求重跑整个批次。

### R17 Concur 收据邮件

WHILE 处于内部 Alpha，THE SYSTEM SHALL 默认不向真实 Concur 地址发送邮件，除非产品负责人为该次测试明确批准。

BEFORE 公开 Beta，THE SYSTEM SHALL 支持从用户已验证邮箱先发送一张收据，等待用户确认“只进入收据库”或识别 ExpenseIt 行为，再允许批量发送。

WHEN 批量发送，THE SYSTEM SHALL 限制每封附件数量、记录成功项幂等键、重试失败项，并禁止重复发送已成功项。

THE SYSTEM SHALL NOT 把收据邮件发送成功表述为已经创建、填写或关联指定Concur费用。

### R18 程序与数据分离

WHEN 应用首次启动，THE SYSTEM SHALL 默认将持久数据写入 `%LOCALAPPDATA%\\InvoiceAssistant\\Data`，而不是程序目录。

WHEN 用户替换或删除程序目录，THE SYSTEM SHALL 保留数据库、原件、设置和任务状态。

IF 数据目录属于 UNC、网络共享、只读介质或已知同步盘，THEN THE SYSTEM SHALL 阻止数据库直接运行或要求迁移到本机目录。

### R19 MVP 备份导入

WHEN 用户导出 MVP 备份，THE SYSTEM SHALL 生成带格式版本、文件清单和完整性校验的未加密备份包，并明确提示其中包含个人发票数据。

THE BACKUP SHALL NOT 包含邮箱授权码、OAuth Token、会话秘密或临时缓存。

WHEN 用户在另一台电脑主动选择备份，THE SYSTEM SHALL 在临时目录校验、预览和导入；失败不得修改现有数据。

THE SYSTEM SHALL NOT 宣称该备份已验证为同一产品用户；严格账号匹配留待账号与加密版本。

### R20 删除和数据保留

WHEN 用户删除免安装程序目录，THE SYSTEM SHALL NOT 自动删除用户数据。

WHEN 用户选择“退出并清除程序与数据”，THE SYSTEM SHALL 显示将删除的程序目录、数据目录、数据类别和不可恢复后果，提供先导出备份的入口，并要求二次确认。

WHEN 用户完成二次确认，THE SYSTEM SHALL 关闭数据库和应用进程，再由受控清理工具仅删除已验证的本产品程序目录和数据目录；不得扩大到用户目录、磁盘根目录、网络路径、联接点或符号链接目标。

IF 任一目标路径验证、文件占用或删除步骤失败，THEN THE SYSTEM SHALL 停止扩大删除范围，保留未删除数据并显示可审计的失败结果。

THE SYSTEM SHALL 默认保留本地数据，直到用户主动删除；临时文件按任务生命周期清理。

### R21 网络与遥测

THE SYSTEM SHALL 默认关闭匿名遥测，不自动上传使用统计、错误、发票或用户信息。

WHEN 用户点击“检查更新”，THE SYSTEM SHALL 只读取版本清单并展示结果；不得静默下载、替换程序或请求提权。

所有生产网络连接、域名、端口、目的和发送字段必须进入用户隐私说明和 IT 审核包。

### R22 诊断与隐私

WHEN 生成诊断信息，THE SYSTEM SHALL 仅包含版本、Windows/WebView2 版本、阶段、错误码和脱敏路径。

THE SYSTEM SHALL NOT 在日志和诊断中包含授权码、邮件正文、完整发票号、税号、金额明细或原始附件。

### R23 免安装运行

WHEN Windows 11 x64 标准用户解压官方 ZIP 并启动 EXE，THE SYSTEM SHALL 无安装、无 UAC、无服务/驱动、无开机启动和无文件关联地运行。

IF Windows 或组织策略在进程启动前阻止程序，THEN 用户文档 SHALL 提供签名、哈希和 IT 审核材料，不提供绕过安全控制的方法。

### R24 WebView2

WHEN 应用启动，THE NATIVE BOOTSTRAP SHALL 在创建 WebView 窗口前检测系统 Evergreen WebView2 Runtime。

IF Runtime 缺失，THEN THE SYSTEM SHALL 使用原生界面显示微软官方获取方式、企业离线说明和退出操作，不静默安装或提权。

### R25 签名与发布包

WHILE 处于内部 Alpha，THE RELEASE PIPELINE MAY 生成明确标记的未签名测试包。

BEFORE 对外 Beta 或正式发布，THE RELEASE PIPELINE SHALL 对所有自有 PE 文件执行可信 Authenticode 签名和时间戳，并在签名后生成 SHA-256。

IF 签名、时间戳、发布者、哈希、SBOM 或第三方许可校验失败，THEN THE RELEASE PIPELINE SHALL 阻止发布。

### R26 下载与更新

WHILE 处于 Alpha，THE PRODUCT SHALL 使用指定 GitHub Release 作为候选包来源。

BEFORE 正式发布，THE PRODUCT SHALL 提供官方 HTTPS 下载页、版本说明、独立哈希、隐私政策和用户协议。

WHEN 用户手动更新，THE SYSTEM SHALL 允许新旧程序目录并存，迁移前创建数据库快照，并在失败时保留原数据和回退路径。

### R27 UI 与无障碍

THE UI SHALL 继承已确认的工业化财务工作台设计、颜色、字体、三栏审核布局和 Lucide 图标规范。

WHEN 用户只使用键盘、125%/150% 缩放、高对比度或减少动态效果，THE SYSTEM SHALL 保持全部核心功能可用且主操作可见。

### R28 发布质量与批准

BEFORE 正式发布，THE RELEASE CANDIDATE SHALL 满足决策记录 D17 的全部质量门槛，P0/P1 缺陷为零。

BEFORE 从 Alpha 进入 Beta，THE PRODUCT SHALL 完成 5 名用户、每人至少 3 个真实批次的验收，并记录归组调整、审核耗时和阻断问题。

WHEN 研发和测试提交完整证据，THE PRODUCT OWNER SHALL 作最终 Go/No-Go 决定；研发不得自行把候选包标记为正式版。

### R29 Concur报销单草稿创建、费用填写与发票关联

WHEN 用户已完成审核、持有有效 `ReviewSnapshot`，并在独立交付选择中选择“上传到Concur”，THE SYSTEM SHALL 先显示目标租户、映射档案版本、报销单名称、报销单日期、费用数、附件数、实际总金额和该目标的映射准备度，并要求用户明确确认。

WHEN 用户确认上传，THE SYSTEM SHALL 创建一个未提交Concur报销单草稿，只为计入状态的本地费用项各创建一个费用条目，使用已冻结的映射投影填写目标字段，并把对应发票单的主发票及配套材料上传且关联到同一费用条目。

THE SYSTEM SHALL 使用发票实际价税合计作为初始申报金额，不得执行企业报销限额、填写核准金额或点击最终提交。

THE SYSTEM SHALL 为报销单、费用和附件记录外部稳定标识、阶段状态、幂等键、重试次数和最后错误；中断恢复、重复点击和局部重试不得生成重复报销单、费用或附件。

IF Concur返回结果未知、租户字段发生变化、必填项缺失或附件关联无法验证，THEN THE SYSTEM SHALL 停止相关步骤，回读核对或要求用户人工处理，不得猜测成功或盲目重建。

WHEN 上传完成，THE SYSTEM SHALL 回读并逐项展示报销单、费用字段和附件关联结果，提供“在Concur中打开并检查”，且Concur对象保持未提交草稿状态。

THE SYSTEM SHALL NOT 持久化Concur密码、SSO凭据或可复用浏览器会话Cookie；操作必须由用户触发、在用户可见且当前授权的会话中执行。

### R30 发票单聚合、票据挂载与金额计入口径

WHEN 系统导入主发票、行程单、消费明细、其他配套材料或同一发票的来源副本，THE SYSTEM SHALL 将它们表示为 `DocumentAsset`，并挂载到一个 `InvoiceRecord` 发票单聚合。

THE SYSTEM SHALL 为一个发票单只生成一笔默认费用和一次票面金额；行程单、明细、其他配套材料和重复来源副本不得独立增加发票张数、费用条目或申报总额。

IF 系统无法确定配套材料属于哪个发票单，THEN THE SYSTEM SHALL 将其放入“待挂载材料”，要求用户选择归属，不得把它作为独立费用继续处理。

THE SYSTEM SHALL 使用明确计入状态：`included`、`suspected_duplicate_excluded`、`confirmed_duplicate_excluded`、`user_confirmed_distinct_included`、`manually_excluded`。

THE SYSTEM SHALL 按精确小数计算：`申报总额 = Σ(included + user_confirmed_distinct_included 发票单的实际价税合计)`；疑似/确认重复和其他排除状态的金额必须在UI、输出和Concur上传中排除，并单独显示数量与金额。

WHEN 发票单移动到某个行程组，THE SYSTEM SHALL 连同其全部配套材料一起移动；配套材料不得作为独立归组对象。

### R31 稳定本地费用字段与目标系统映射

WHEN 系统为计入状态的 `InvoiceRecord` 建立费用，THE SYSTEM SHALL 创建目标系统无关的版本化 `ExpenseItem`，至少表达内部费用分类、实际发生日期、费用说明、交易对方、发生地点、付款方式、实际金额、币种、票面税项、关联行程、计入状态以及字段来源和确认状态。

THE SYSTEM SHALL 将发票号码、开票日期、购销方税号和原件解析证据保留在 `InvoiceRecord`，将报销业务语义保留在 `ExpenseItem`；本地字段不得以Concur显示名称、外部选项ID、目标必填性或页面结构作为数据库字段语义。

WHEN 用户核对单条费用，THE UI SHALL 显示“费用信息、票据信息、问题与依据”，使用本地字段名称和本地完成规则，不得显示“Concur填报字段”或用目标租户必填性控制本地审核完成。

WHEN 用户选择目标Concur企业档案并启动上传预检，THE SYSTEM SHALL 使用版本化 `ConcurMappingProfile` 将已确认 `ExpenseItem` 生成 `MappedExpensePayload`，并逐项显示内部来源字段、转换规则、外部目标字段、映射结果和缺口。

IF Concur要求本地模型没有的企业自定义字段，THEN THE SYSTEM SHALL 仅在该上传会话中要求补充或从企业档案取默认值；该缺口不得阻断本地输出，也不得静默回写为本地费用核心字段。

WHEN 用户切换租户、更新映射或重新上传，THE SYSTEM SHALL 重新生成外部投影而不修改已审核 `ExpenseItem`；每次上传必须保存映射档案版本、规则版本、费用项版本、上传补充值和最终映射快照以供回读对账。

THE SYSTEM SHALL NOT 把Concur费用类型ID、地点/VAT/付款/票据状态选项ID、核准金额、目标必填标记或企业自定义字段存入 `ExpenseItem`；这些数据只能存在于目标配置、上传会话和外部结果快照。

### R32 批次双视图、审核完成与交付选择

WHEN 用户进入一个批次，THE UI SHALL 只提供`费用清单`和`归组`两个一级视图；问题、重复、待挂载材料、字段核对和审计记录必须作为视图内筛选、检查器或详情呈现，不得增加“输出与Concur”“记录”或其他批次一级标签。

WHILE 批次存在本地审核阻断项或尚未由用户确认完成审核，THE UI SHALL NOT 在批次内显示Excel导出、Concur上传或创建外部草稿的主操作；批次结束操作只能为“完成审核”，并明确显示阻断原因。

WHEN 所有本地阻断项已解决且用户点击“完成审核”，THE SYSTEM SHALL 在同一事务边界内冻结带版本、内容摘要和创建时间的 `ReviewSnapshot`，记录其费用项、发票单、计入状态、归组、附件和金额汇总版本，并导航到独立的“交付选择”页面。

WHEN 交付选择页面打开，THE UI SHALL 把`导出 Excel`和`上传到 Concur`作为两个并列主入口；Excel入口不得要求Concur企业档案、映射或登录会话，Concur入口必须在用户选择目标档案后执行R29和R31的映射预检。

WHEN 用户完成一种交付，THE SYSTEM SHALL 允许返回同一交付选择页执行另一种；每种交付必须使用审核快照和稳定任务键独立执行，不得静默覆盖既有文件或重复创建Concur报销单、费用和附件。

IF 用户在完成审核后修改任何影响费用字段、票面事实、计入状态、归组或关联附件的本地数据，THEN THE SYSTEM SHALL 立即把原 `ReviewSnapshot` 标记为失效，并阻止基于该快照启动新的Excel导出或Concur上传，直到用户重新完成审核；已生成的交付记录和文件不得被删除或伪装为当前结果。

WHEN 用户从交付选择返回批次，THE UI SHALL 恢复离开前的一级视图、筛选条件、滚动位置和选中费用；交付任务和结果虽然关联批次，但不得成为批次内部一级视图。

### 7.1 Alpha
