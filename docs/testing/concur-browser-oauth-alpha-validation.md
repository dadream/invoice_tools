# Concur 浏览器 OAuth Alpha 验证

> 目的：确认目标企业环境是否允许发票报销助手通过系统浏览器完成 SAP Concur 官方 OAuth 授权，并判断现有浏览器登录状态能否减少重复登录。

## 1. 验证边界

- 只使用 SAP Concur 官方 Authorization Code 流程，不读取浏览器 Cookie、本地存储、开发者工具数据或网络缓存。
- 浏览器登录状态只用于 Concur/公司 SSO 自行识别当前用户，不能替代 OAuth 应用注册和企业授权。
- 浏览器测试阶段只执行报销单只读探测，不创建或修改 Concur 数据。
- Client Secret、访问令牌和刷新令牌不写入本地数据库、备份或日志；程序退出后访问能力失效。
- 只有用户另行确认第三段测试时，才创建带“发票助手能力测试”名称的未提交草稿、0.01 元费用和测试 PDF；软件不最终提交报销单。

## 2. 前置条件

1. Alpha 用户可以在系统默认浏览器正常访问目标企业 Concur。
2. Concur 管理员提供企业批准的测试应用 Client ID 与 Client Secret。
3. 管理员为测试应用登记软件页面显示的固定回调地址：`http://127.0.0.1:53682/concur/oauth/callback`。
4. 测试应用至少申请 `EXPRPT`、`IMAGE`；最终以页面的权限检查和实际接口探测结果为准。
5. 本机安全软件和企业策略允许程序短时监听 `127.0.0.1:53682`。该监听只在一次授权测试期间存在，最长 5 分钟。

## 3. 执行步骤

1. 先在系统默认浏览器登录 Concur，保持会话有效，不打开浏览器开发者工具。
2. 打开发票报销助手“设置 → Concur 能力”。
3. 确认数据中心地址；输入 Client ID 和 Client Secret。
4. 核对页面展示的回调地址和申请权限，勾选确认后点击“打开系统浏览器并测试授权”。
5. 记录浏览器是否要求重新输入账号、密码或再次完成公司 SSO。
6. 在 Concur 官方授权页完成允许/同意操作，等待浏览器显示“Concur 授权已返回”。
7. 返回软件，核对以下步骤是否通过：
   - 浏览器登录与授权回调；
   - 交换临时授权码；
   - 检查接口权限；
   - 读取当前用户报销单。
8. 核对页面顶部“已连接的账号”是否为浏览器中选择的报销账号；如果该账号没有历史报销单，先完成草稿测试，再核对通过新建草稿识别出的账号。
9. 核对四项能力卡：报销单读取、草稿创建、费用创建、发票上传。创建类能力只有创建和回读均成功时才应显示“通过”；前一步失败时，后续项应显示“未测试”。
10. 关闭并重新启动软件，确认状态恢复为未连接，证明令牌未被持久化。

## 4. 结果记录

每名 Alpha 用户只记录以下非敏感信息，禁止截图或复制 Client Secret、授权码和令牌：

| 字段 | 记录内容 |
|---|---|
| 测试日期 | 日期即可 |
| 企业/租户代号 | 使用内部非敏感简称 |
| Concur 数据中心 | 例如中国区 |
| 测试前浏览器已登录 | 是/否 |
| 授权时是否重新登录 | 是/否 |
| 回调是否成功 | 是/否及页面错误文案 |
| 权限检查 | 通过/未列出/缺少权限 |
| 未提交报销单只读探测 | 通过/失败及软件错误文案 |
| 重启后是否断开 | 是/否 |

## 5. 通过标准与产品决策

- “可复用浏览器登录状态”：测试前已登录，授权时未要求重新登录，且回调、授权码交换、权限检查或实际权限探测全部通过。
- “OAuth 可用但不保证免登录”：授权时要求重新登录，但其余步骤通过。
- “暂不支持”：同一企业环境在核对应用凭据、回调登记、权限和数据中心后，仍因策略阻止本机回调或无法完成授权码交换。
- 没有企业批准的 OAuth 应用凭据属于“未满足测试前提”，不能归类为支持或不支持。

至少应覆盖 2 个不同 Alpha 用户；若计划支持多个企业租户，应至少覆盖 2 个租户。正式方案只能在样本完成后确定，并需单独决定 Client Secret 应由企业配置、受控后端托管，还是采用 Concur 支持且经安全评审的其他客户端模式。
