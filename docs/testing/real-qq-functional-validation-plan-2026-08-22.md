## 1. 结论

四项验证方向合理，而且应优先于归组、输出和 Concur 验证。不过不能只报告一个笼统“准确率”：邮件识别、附件获取、文件识别和字段解析是四个不同分母，混在一起会掩盖问题。邮件与附件分类必须同时报告精确率、召回率、F1 和混淆矩阵；解析必须按 L0/L1/L2、文件格式和核心字段分别报告。

真实数据可以用于内部 Alpha 验证，但不能成为自动生成“正确答案”的来源。金标准必须由人工在不知道产品预测结果的情况下独立标注，之后再揭示预测并复核分歧。产品自己的分类或解析结果不能反过来证明产品准确。

## 2. 安全前置门禁

以下条件任一不满足，不得开始读取邮件正文：

1. 用户本次明确给出约定的精确授权语句。
2. 账号掩码、日期半开区间和授权语句一致。
3. 客户端只使用 `EXAMINE`、`UID SEARCH`、只读 `UID FETCH` 和 `BODY.PEEK[]`。
4. 生产路径不暴露 `STORE`、`COPY`、`MOVE`、`APPEND`、`DELETE`、`EXPUNGE`。
5. 授权码只从 `.env.local` 的 `INVOICE_IMAP_PASSWORD` 进入子进程内存，不进入命令行、数据库、报告、截图或 Git。
6. 读取前建立 UIDVALIDITY、文件夹计数、范围 UID、FLAGS、RFC822 大小和 Message-ID 摘要指纹；读取后完全一致，否则整轮失败。
7. 真实附件只写入仓库外的唯一隔离目录；不写 `fixtures`、`artifacts` 或用户正式 DataRoot。`artifacts` 只允许保存脱敏汇总。
8. 不访问 SMTP，不发送、回复或转发邮件，不访问 Concur。

首轮只读普查由 `scripts/run-real-qq-readonly-validation.ps1` 显式启动，普通 CI 和 `scripts/verify-windows.ps1` 均不得自动运行它。

## 3. 四类指标与正确分母

### 3.1 发票邮件识别

人工金标准先把范围内每封邮件标为：

- `invoice_attachment`：直接带可取得发票/报销凭证附件；
- `invoice_link_only`：仅正文链接、二维码或小程序入口交付；
- `invoice_notice_only`：通知类邮件，不可直接取得凭证；
- `not_invoice`：非发票邮件；
- `uncertain`：需二次裁决，不进入首轮指标。

产品预测至少拆成“识别为发票邮件”和“识别为可直接下载附件的发票邮件”。主要指标：

- 精确率 `TP / (TP + FP)`：产品判为发票邮件的结果中有多少是真的；
- 召回率 `TP / (TP + FN)`：真实发票邮件中有多少被找到；
- F1：精确率和召回率的调和平均；
- `link_only` 单列覆盖率：不能把尚未支持的链接下载算成附件下载失败。

普通邮件占多数时，整体 Accuracy 容易虚高，只作为补充，不作为发布门禁。

### 3.2 发票附件获取与下载

按三段分别计算，避免把 IMAP、MIME 和落盘问题混为一谈：

1. 邮件原文获取成功率：成功 `BODY.PEEK[]` 的邮件数 / 搜索命中的邮件数；
2. MIME 附件提取成功率：成功解码的直接附件数 / 人工确认应存在的直接附件数；
3. 隔离落盘成功率：非空且写后 SHA-256 可复核的文件数 / 成功解码附件数。

ZIP 另报告容器打开、条目数量限制、展开大小限制、路径穿越拒绝和支持格式条目提取。链接型发票单列为安全提示与人工下载降级，不进入直接附件下载分母，也不得记为自动下载成功。

### 3.3 已下载文件是否为有效发票

每个文件由人工标注为：

- `valid_invoice`：有效发票或正式报销凭证；
- `supporting_document`：行程/订单/结算辅助材料但不是发票；
- `not_invoice`：Logo、广告图、邮件签名等；
- `corrupt_or_empty`：空文件、损坏或解码失败；
- `unsupported`：可能有效但当前产品不支持的格式或加密文件；
- `uncertain`：待裁决。

产品预测报告发票精确率、召回率、F1、无效文件拒绝率和各格式混淆矩阵。扩展名与 MIME 只能作为特征，文件魔数、容器结构和解析结果必须参与判断，不能把“解析成功”直接等同于“有效发票”。

### 3.4 直解析、OCR 与字段准确率

有效发票文件按实际处理路径统计：

- L0：XML、OFD 内嵌 XML 等结构化直读；
- L1：PDF 文本层和版式解析；
- L2：图片或扫描 PDF 的本地 OCR；
- L4：冲突、低置信或不完整，必须人工处理。

报告以下比例：

- 直解析比例：`(L0 + L1) / 有效且受支持发票数`；
- OCR 需要比例：`进入 L2 的文件数 / 有效且受支持发票数`；
- 自动解析覆盖率：`得到结构化结果的文件数 / 有效且受支持发票数`；
- 强制人工比例：`L4 或解析失败数 / 有效且受支持发票数`。

人工金标准至少核对发票号码、开票日期、价税合计、税额、购买方和销售方。号码、日期和金额按严格相等判断；名称按明确的空白/全半角规范化后判断。分别报告单字段正确率和“全部核心字段同时正确率”，不能只用平均字段正确率掩盖关键金额错误。

产品定义门槛沿用：L0 核心字段 100%；L1 目标不低于 99%；L2 目标 92%–95%，且所有 L2 与低置信结果进入人工审核。样本量小于 30 时同时报告分子/分母和 95% Wilson 区间，不用一个整数百分比下结论。

## 4. 执行顺序

### 阶段 A：只读普查

1. 在允许直连 `imap.qq.com:993` 的网络上运行 TLS 预检。
2. 执行只读启动器，得到范围邮件数、含附件邮件数、附件数、候选数、重复数和前后邮箱指纹。
3. 若任何邮箱指纹变化、拉取失败或 MIME 失败，停止，不进入准确率评估。

### 阶段 B：隔离采集与盲标

1. 创建仓库外唯一 DataRoot，只保存本轮原始附件、内容哈希和私有复核清单。
2. 第一遍隐藏产品预测，人工完成邮件级和文件级金标准。
3. 第二遍揭示预测，只裁决分歧；所有分母冻结后再计算指标。
4. 公共报告只输出计数、比例、错误类别、掩码和不可逆哈希。

### 阶段 C：解析与 OCR

1. 对人工确认的有效文件依次执行 L0、L1、L2 路由，记录实际路径和耗时。
2. 人工逐字段核对，不把 OCR 置信度当作正确答案。
3. 按格式、来源、解析级别分别统计，建立失败样本的脱敏回归用例。

### 阶段 D：重复性与 Windows UI

1. 同一免安装候选包、同一范围连续执行两轮。
2. 第二轮结果集合和内容哈希应一致，去重稳定，邮箱指纹仍一致。
3. 再从 Windows UI 覆盖授权码遮罩、北京配置、进度、取消/恢复、人工审核和结果页；UI 自动化日志与截图不得包含真实内容。

## 5. 发布判断

以下任一情况判定 No-Go：

- 邮箱前后任一只读指纹变化；
- 授权码或真实邮件/发票明细进入仓库、日志、截图或公开报告；
- 有搜索命中邮件未成功 PEEK 获取且不能解释为外部网络故障；
- 有直接发票附件静默漏下、空文件被当成成功或下载后哈希不可复核；
- 关键金额、号码或日期出现静默错误且未进入人工审核；
- 链接型邮件被统计为“下载成功”，或被隐藏在直接附件失败率中；
- 两轮结果集合、去重或指纹不一致。
