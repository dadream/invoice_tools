# OCR 性能与进程隔离验证（2026-08-20）

> 结论：参考 Windows 11 机器上的非隐私合成基准满足“50 张不超过 5 分钟”的时间目标；OCR 已改为单并发独立 worker、每文件 45 秒硬超时。该证据不替代真实混合批次、最低配置机器或两台物理电脑验证。

## 1. 参考环境

- Windows 11 专业版 10.0.26100
- Intel Core Ultra 5 125H，18 个逻辑处理器
- 物理内存 16,648,040,448 字节
- OCR：RapidOCR PP-OCRv5 mobile + ONNX Runtime 1.22.0 CPU
- 检测最长边 1800；intra-op 2、inter-op 1；CPU arena 和 memory pattern 关闭
- worker 最大并发 1；每文件硬超时 45 秒

机器可读证据：`artifacts/ocr-performance-2026-08-20.json`。报告包含 fixture、OCR 源码、worker 协议/实现、验证脚本和 Cargo.lock 的 SHA-256，用于绑定当前实现。

## 2. 生产 worker 结果

每次迭代都启动新的 `invoice-ocr-worker.exe`，通过 stdin 发送版本化 JSON 请求，通过 stdout 接收结果；因此包含模型冷启动和进程创建成本。

| 输入 | 次数 | 平均 | P95 | 最大 | 单进程峰值工作集 | 50 张估算 |
|---|---:|---:|---:|---:|---:|---:|
| 合成发票图片 | 5 | 3.594 s | 3.916 s | 3.916 s | 394,842,112 B（约 377 MiB） | 179.7 s |
| 合成扫描 PDF | 3 | 4.246 s | 4.516 s | 4.516 s | 533,049,344 B（约 508 MiB） | 212.3 s |

两类估算均小于 300 秒目标。所有迭代同时核对发票号、日期、金额、税额、购销方、L2 和置信度 ≥0.85，不是只测空调用。

## 3. 内存优化证据

初始配置使用检测最长边 2000 和 ORT 默认 CPU arena，图片/PDF 峰值分别为 937,156,608 B 与 1,248,034,816 B。最终配置将最长边设为 1800，显式关闭 CPU arena 和动态输入 memory pattern；独立 worker 进一步保证每文件完成后操作系统回收模型内存。

1024、1280、1536、1600 均实际运行过同一图片 golden，但置信度分别低于 0.85 门槛，因此未通过降低分辨率或降低测试阈值制造性能结果。1800 同时通过图片和扫描 PDF golden。

## 4. 隔离与超时

- 主程序只从自身目录启动固定文件名 `invoice-ocr-worker.exe`，不通过 PATH 搜索。
- Release 模式要求 portable `manifest.json` 声明 worker，启动前核对 SHA-256；符号链接、缺失、篡改或超大 manifest 均拒绝。
- 全局非阻塞槽保证最多一个 OCR worker；并发请求立即得到“正在处理”提示，不堆积高内存进程。
- 主程序每 25 ms 检查 worker；45 秒未退出就调用进程终止并回收，返回可操作错误。
- stdin 请求上限 64 KiB，stdout 响应上限 1 MiB；worker panic 被截获并转换为无原始内容的错误。
- 自动回归覆盖协议往返、并发拒绝、真实子进程超时终止、manifest 正确/篡改和图片/PDF 完整 IPC golden。

## 5. 仍未关闭的发布门禁

1. 至少 10 张真实/私有受控票据的字段准确率和需复核率。
2. 真实 50 文件混合批次的端到端耗时，而非单一 fixture 线性估算。
3. 最低支持配置及至少两台物理 Windows 电脑的耗时、峰值和 UI 响应。
4. 超时、worker 崩溃、磁盘不足和用户取消在 packaged GUI 中的人工提示走查。
5. 公开版本对主程序和 worker 使用同一 Authenticode 主体签名并加时间戳。
