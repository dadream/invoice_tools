# 发票报销助手产品设计一致性规范

> 状态：现行规范
> 版本：1.0
> 生效日期：2026-09-03
> 适用范围：Windows 免安装本地版的产品设计、UI 实现、交互评审和发布验收

## 1. 目的与规范优先级

本文把已确认的产品优化决策沉淀为可执行规范，用于避免页面各自设计、相同组件表现不同、工作区被低价值信息占用、流程相互依赖以及技术实现直接暴露给用户。

规范用语：

- **必须**：不满足即不能作为完成状态交付。
- **应该**：默认遵守；偏离时必须有明确的产品理由。
- **禁止**：已验证会造成理解、操作或一致性问题的做法。

文档优先级：

1. 业务范围、状态机和发布边界以 `specs/mvp-release-baseline/` 为准。
2. Concur 字段转换以 `docs/concur-field-mapping-design.md` 为准。
3. 页面结构、视觉一致性和交互行为以本文为准。
4. 历史优化方案仅用于追溯，不得覆盖上述现行规范。

本文不要求产品界面显示“MVP”“内部阶段”等研发术语。

## 2. 总体产品原则

### 2.1 围绕用户任务，而非技术流水线

用户面对的主对象只有“邮件收集任务”和“报销批次”。解析器、检查点、数据库、OCR、MIME、算法版本、置信度等实现细节不得成为页面主信息。

完整流程固定为：

```text
邮件收集与来源审核 / 本地文件
→ 导入报销批次
→ 解析、去重和生成费用
→ 费用核对
→ 归组审核
→ 完成审核
→ 选择导出或上传到 Concur
```

### 2.2 信息服务于当前决定

- 每个页面必须明确回答：用户现在处于哪里、需要判断什么、下一步是什么。
- 首屏优先展示当前任务、关键状态和主要操作。
- 说明性内容应该短、具体，并为主要工作区让出空间。
- 重复表达相同状态的标题、卡片、提示和计数必须合并。

### 2.3 一页一个主要目标

- 列表页负责查找、筛选、进入对象和创建对象。
- 审核页负责处理当前审核对象。
- 设置页负责长期规则和资料。
- 交付页只在审核完成后负责 Excel、打印 PDF 或 Concur 交付。
- 不得为了减少页面数量，把创建、导入、审核、预览和交付同时堆在一个页面。

### 2.4 相同语义必须使用相同表现

相同层级的页面标题、主按钮、统计卡、搜索框、筛选框、表头、主链接、状态标签和操作链接必须复用相同的结构与视觉规格。新增页面不得复制后再自行微调形成新的变体。

### 2.5 用户保持最终控制

- 自动识别结果必须可查看、可修正、可排除和可恢复。
- 系统不得替用户执行企业报销上限、最终提交或审批决定。
- 长任务必须显示进度、结果和失败后的可执行动作。
- 删除、覆盖等不可逆操作必须确认；可恢复的排除操作应直接完成并提供明确反馈。

## 3. 核心对象与页面边界

### 3.1 邮件收集任务

邮件收集是独立任务，负责：

- 按日期范围只读搜索邮箱；
- 分类邮件；
- 下载并校验附件完整性；
- 在首次分析时提取并持久化邮件正文链接；
- 让用户审核邮件、补充材料、过滤无效附件并完成来源确认。

邮件收集阶段禁止解析费用、生成费用项或执行归组。除非用户明确选择“重新分析”，进入审核页不得重新下载或重新分析邮件。

已完成来源审核的任务必须保留为可追溯来源，不显示删除按钮，也不支持删除。

### 3.2 报销批次

新建批次任务只包含：

- 批次名称：用户输入；
- 创建时间：系统生成。

日期范围、邮箱、发票来源和本地文件属于批次内的导入行为，不属于创建批次表单。

批次内只保留两个一级审核视图：

1. 费用清单：确认软件稳定费用字段，包括类型、日期、实际金额、交易方和地点。
2. 归组：确认费用之间的行程或消费归属关系。

费用清单保存不得依赖归组确认；归组保存不得反向校验费用日期或类型。

### 3.3 材料、费用与归组

- 本地导入对象是发票及配套材料文件，不是 `.eml`。
- 发票、行程单、明细和水单必须挂载在同一个发票单或费用上下文中，保持来源关联。
- 待处理材料与“本次费用”“未计入”并列展示，支持挂载、转为费用或明确忽略。
- 滴滴行程单等能够独立证明纸质票费用的材料必须允许转为费用。
- 疑似重复默认不计入金额；只有用户明确标记为非重复后才恢复计入。
- 未计入费用从本次费用清单移出，在“未计入”视图管理；无需强制填写排除原因。
- 归组名称是用户可理解的稳定名称，并在费用清单与归组页保持一致。
- 行程日期和路线优先采用行程单、火车票、机票等强证据；住宿和目的地消费可在证据充分时归入已有差旅组。

### 3.4 Concur 边界

单条费用核对使用软件自己的稳定字段，不显示 Concur 专属字段。完成审核后，系统才依据可配置映射创建 Concur 草稿、填写费用并上传对应发票。

软件提取并申报发票实际金额。企业餐费上限等公司政策由用户进入 Concur 后处理。

Concur 能力测试必须与真实批次交付分开：页面顶部固定显示当前授权账号，并分别显示“报销单读取、草稿创建、费用创建、发票上传”的通过、失败或未测试状态，再决定是否开放交付。创建类能力只有写入并回读成功才能算通过。浏览器 OAuth 测试只能走官方授权回调，不读取浏览器 Cookie；必须明确说明“已有登录状态可能减少重复登录，但不能替代企业 OAuth 应用和权限审批”。测试凭据和令牌不得持久化，单段测试通过不得显示为全部能力通过。

## 4. 应用框架规范

### 4.1 Windows 窗口

- 程序默认最大化启动。
- 用户可以还原、缩放、最小化和关闭窗口。
- 界面必须适配窗口还原后的最小支持尺寸，不得假设永远全屏。

### 4.2 左侧导航

- 左侧导航必须支持折叠和展开。
- 折叠后保留可识别图标、当前项状态和提示文本。
- 主内容宽度必须随导航状态自适应，不保留无效空白。

### 4.3 页面容器

- 一级列表页使用一致的最大内容宽度和桌面内边距；当前基准为最大宽度 `1500px`、内边距 `2rem`。
- 窄窗口下内边距降为 `1rem`，工具栏允许换行或纵向排列。
- 主要审核工作区应尽量使用可用高度，禁止让低频说明占据大量首屏空间。

## 5. 一级列表页统一结构

邮件收集页和报销批次页必须使用相同的页面骨架：

```text
产品域眉题
页面标题 + 一句职责说明                         新建按钮
统计筛选区
搜索框 + 状态筛选                              共 N 项
表格
```

### 5.1 标题区域

- 保留产品域眉题：如“来源材料工作台”“本地报销工作台”。
- 页面标题分别为“邮件收集”“报销批次”。
- 标题下只保留一句当前页面职责说明。
- 新建按钮置于右侧，与标题区垂直对齐。
- 禁止显示“一次性任务”“MVP 固定规则”等研发或阶段文案。

### 5.2 新建按钮

同级页面的新建按钮必须完全一致：

| 属性 | 当前标准 |
|---|---|
| 内边距 | `0.68rem 0.9rem` |
| 边框/背景 | `#136B52` |
| 文字 | 白色、`font-weight: 700` |
| 文案格式 | `＋ 新建…任务` |

不得仅凭文字长度为某个页面单独改变高度、内边距或字重。

### 5.3 统计区域

- 统计卡使用单行信息，保持紧凑且等高。
- 邮件收集：正在收集、待来源审核、审核完成、失败/中断。
- 报销批次：草稿批次、已完成审核、当前合计。
- 可点击的统计卡用于过滤下方表格，并显示选中状态。
- 数量为 `0` 且点击不会产生有效结果时，必须禁用，不显示可点击反馈。
- “当前合计”等非过滤指标不可伪装成可点击控件。

### 5.4 列表工具栏

- 搜索框和状态筛选放在最左侧；“共 N 项”放在最右侧。
- 两个一级列表页使用一致尺寸：搜索框宽 `260px`、状态筛选宽 `150px`、高度 `38px`。
- 删除“收集任务”“批次管理”“按照最近更新排序”等不提供操作价值的重复标题。
- 搜索和筛选应即时生效；空结果需要显示当前条件下无匹配项，而不是空白区域。

### 5.5 表格表头

所有一级列表表头采用同一视觉标准：

| 属性 | 当前标准 |
|---|---|
| 内边距 | `0.75rem 1rem` |
| 背景 | `#F1F3F4` |
| 文字色 | `#596870` |
| 字号 | `0.74rem` |
| 换行 | `white-space: nowrap` |
| 对齐 | 默认左对齐，与对应数据列一致 |

排序必须由表头直接触发，使用一致的未排序、升序、降序指示。禁止在表格上方另写“按最近更新排序”。

允许排序的字段固定为：

- 邮件收集：任务、日期范围。
- 报销批次：批次、创建时间。

其他列不显示排序暗示，也不响应排序操作。

报销批次表列顺序固定为：批次、创建时间、费用数、计入金额、状态、操作。状态必须紧邻操作列，并与批次详情使用相同的状态名称和颜色口径。

### 5.6 首列主链接

邮件任务和报销批次名称以邮件收集页为统一基准：

| 层级 | 当前标准 |
|---|---|
| 主名称 | 松针绿 `#136B52`、粗体、`1.05rem` |
| 次级信息 | `#6C7980`、原辅助字号 |
| 名称与次级间距 | `0.15rem` |
| 控件 | 无背景、无边框、左对齐、手型光标 |

主名称本身必须可点击进入详情。不得出现同级对象一个是黑色文字、另一个是绿色链接，或字号、行距不同的情况。

点击区域不应只覆盖单个字符；按钮应包裹主名称和次级信息形成连续点击目标。

### 5.7 日期时间

- 一级列表默认只显示用户决策所需的日期，格式为 `YYYY-MM-DD`。
- 报销批次“创建时间”只显示日期，不显示时分秒。
- 只有操作审计、运行日志或顺序冲突确实需要时，才显示具体时间。
- 显示存储日期时不得因不必要的时区转换造成日期前后偏移。

### 5.8 操作列

- 操作列与其他列保持相同左对齐基线。
- 同级文字操作用 `|` 分隔，如“查看 | 交付”。
- 不添加多余下划线、整行边框或看似禁用的装饰线。
- “查看”进入审核结果；“交付”进入已完成审核后的交付页，两者语义不得混用。
- 危险操作必须使用风险色，并与常规操作保持足够间距。

## 6. 详情与审核页规范

### 6.1 列表进入独立审核页

数据量较大时，列表页只承担浏览和筛选。点击一条记录进入独立审核页，不在同一页面用狭窄左右对照区同时展示长列表和完整详情。

审核完成后的“下一条”必须：

- 自动进入当前筛选队列中的下一条；
- 不跳入已审核、已排除或其他分组；
- 没有下一条时明确提示队列已完成。

### 6.2 原件查看器

- 费用信息与原件采用清晰的左右对照结构，参考 Concur 的“表单 + 原件”模式。
- 禁止把列表、字段表单和原件强行挤成三个同等窄栏。
- PDF、OFD 和图片必须有明确的可查看路径；不可预览时不得长期占据空白主工作区。
- 查看器至少支持折叠和全屏；折叠后必须保留“查看发票”入口。
- 放大后应支持完整的水平、垂直滚动，不得裁掉左侧或顶部内容。
- 原件读取失败必须说明是文件缺失、格式不支持还是文件损坏，并提供重新关联或外部打开等可执行动作。

### 6.3 费用审核

- 费用清单优先展示：实际日期、费用类型、实际金额、交易方/地点、归组、状态、操作。
- 实际金额紧随费用类型，保证关键判断信息优先可见。
- 列宽依据内容分配，避免无意义宽列造成横向滚动。
- 待确认原因必须使用中文业务语言；文件条目不向普通用户显示 MIME。
- 问题提示下方应提供直接确认操作，禁止要求用户滚动到远处才能完成当前问题。

### 6.4 归组审核

- 归组先使用列表页呈现全部组，组名可点击进入独立审核页。
- 组内费用是主要工作区，应获得主要垂直空间，不得只显示三条高度而让左侧列表占满页面。
- 组内费用默认按类型排序，同类费用内按发生日期排序；允许切换按日期排序。
- “查看发票”“调整归组”与当前费用信息处于同一视觉单元的右侧操作区，避免按钮单独占一整行造成左侧大面积空白。
- “不计入”使用风险样式并与常规操作分隔；可放在同一右侧操作区的末端，但不得与常规按钮混为一组或因展开控件造成整体布局跳动。
- 调整归组控件应浮层或在预留区域展开，不得推挤其他费用内容；已选组名称必须正常显示。
- 确认归组不弹出无必要的确认框，成功后直接进入当前待审核队列下一组。
- “重新生成归组”等低频操作放入紧凑工具区，不占据主要审核视野。

## 7. 状态、反馈与操作行为

### 7.1 状态表达

- 状态不能只靠颜色，必须同时包含文字或形状。
- 状态名称面向业务结果，如“待来源审核”“已核对”“未计入”，不显示内部枚举。
- 页面统计、标签页计数、表格结果必须来自同一状态口径，禁止出现“待处理 14 条但清单全部已处理”。

### 7.2 加载与进度

- 首次读取显示稳定的加载状态，不反复卸载和重建内容造成闪烁。
- 超过约 1 秒的操作应提供处理中反馈；批量解析、Excel/PDF 导出等长任务必须提供进度或阶段状态。
- 完成后明确显示产物位置、成功数量和失败数量。
- 打开邮件链接应直接调用系统浏览器，不重新经过邮件下载或分析流程。

### 7.3 错误信息

错误信息必须包含：

1. 用户能理解的问题；
2. 对当前数据的影响；
3. 下一步可执行动作。

禁止直接把 `invalid stable expense fields`、检查点名称、MIME、堆栈或协议错误作为主提示。技术详情如需保留，应放入可展开诊断信息。

### 7.4 布局稳定性

- 展开筛选、调整归组或更多操作时，不应导致无关内容大幅位移。
- 禁用操作保留必要位置以维持布局，但不能表现得像可点击控件。
- 固定底部操作栏不得遮挡最后一条数据；内容区必须预留对应底部空间。

## 8. 文案规范

- 使用用户语言，不使用研发阶段或技术实现语言。
- 同一对象只使用一个名称：邮件收集任务、报销批次、费用、归组、待处理材料、未计入、交付。
- 按钮采用“动词 + 对象”，例如“新建收集任务”“完成来源审核”“重新生成归组”。
- 描述说明动作和结果，不描述系统架构。
- 所有用户可见原因、状态和错误默认使用中文。
- 日期范围必须明确结束日期是否包含；邮箱搜索继续使用 `[开始日, 结束日)` 时，应在输入或帮助中用自然语言解释。
- 不在产品界面出现“MVP”“固定读取 INBOX”“一次性制度任务”等内部决策文案。

## 9. 交付规范

- 交付入口只在用户完成费用与归组审核后出现。
- 交付选项至少包括导出 Excel、导出打印 PDF、上传到 Concur；能力未启用时必须准确说明，不伪造成功。
- 打印 PDF 默认从发票或材料页开始，不加入不必要的首页和材料目录。
- 如需费用汇总或目录，应导出为独立 PDF，避免用户打印票据时手工排除页面。
- 打印 PDF 必须有全局页码，并保留发票、行程单、水单等材料之间的关联顺序。
- 导出过程显示进度，完成后提供明确的文件位置或打开入口。
- Concur 真实交付只能在独立能力测试通过后启用；能力测试必须把只读连接与会产生未提交草稿的写入测试明确分开。
- 能力测试逐步显示报销单、费用、附件的结果；产生测试草稿前必须由用户明确确认，并给出测试后在 Concur 检查和删除的提示。
- 外部访问令牌不得显示在结果、错误或日志中，也不得写入本地业务数据库和备份。
- Concur 草稿创建必须保持未提交状态；供应商、VAT或租户动态字段未被当前接口写入时，必须明确提示用户到草稿中复核或补充。

## 10. 禁止复发的问题

以下模式已确认不符合产品要求：

- 在新建批次时要求选择日期、邮箱或来源。
- 在邮件收集阶段解析费用或归组。
- 用三栏挤压审核信息，并让不可用预览器占据中心主区域。
- 在列表上方重复显示无操作价值的说明、排序标题或管理标题。
- 相邻一级页面的标题、按钮、搜索框、统计卡、表头和链接各用一套尺寸。
- 只有部分表头可排序却让所有列都显示排序暗示。
- 列表创建时间显示不必要的时分秒。
- 操作按钮单独占一整行，在费用信息下方制造大面积空白。
- 控件展开时推挤内容、清空当前选择或改变整页布局。
- 完成审核后仍要求回到页面顶部手工进入下一条。
- “下一条”跳出当前筛选队列或进入未计入项目。
- 统计卡数量为零仍表现为可点击。
- 已审核完成的邮件收集任务仍显示删除入口。
- 在用户界面显示 MIME、内部错误码、算法名称或研发阶段文案。

## 11. 设计与实现流程

每次新增或调整页面必须按以下顺序执行：

1. 明确页面所属对象、当前用户任务和唯一主操作。
2. 检查是否已有同语义组件；优先复用，禁止创建近似变体。
3. 写明正常、空、加载、失败、禁用和完成状态。
4. 检查筛选、排序、下一条和统计口径是否一致。
5. 检查窄窗口、长文本、大数据量和展开控件时的布局。
6. 完成自动检查和 Windows 编译后，由产品负责人执行真实界面验收。

涉及一级列表页的变更，必须同时对照邮件收集页和报销批次页；涉及审核页的变更，必须同时检查费用审核和归组审核是否继续保持对象边界。

## 12. 发布前 UI 一致性检查表

### 页面级

- [ ] 页面标题、眉题、职责说明和主按钮层级一致。
- [ ] 首屏没有低价值大块说明占用主要工作区。
- [ ] 当前页面只有一个主操作。
- [ ] 默认最大化与还原窗口下均可正常使用。
- [ ] 左侧导航折叠和展开后内容区正确适配。

### 列表级

- [ ] 搜索框、筛选框、统计卡和“共 N 项”位置一致。
- [ ] 表头视觉规格一致，仅允许字段显示排序。
- [ ] 主链接字号、颜色、行距和点击区域一致。
- [ ] 日期只显示当前任务需要的精度。
- [ ] 操作列对齐、分隔和风险操作样式一致。
- [ ] 大数据量下不因无效列宽产生不必要的横向滚动。

### 审核级

- [ ] 当前问题、原件依据和主要操作在同一视野内。
- [ ] PDF、OFD、图片存在可用查看或明确降级路径。
- [ ] 完成后自动进入当前筛选队列下一项。
- [ ] 调整控件不会造成布局跳动或丢失当前值。
- [ ] 费用与归组能够独立保存，不互相阻断。

### 内容与状态

- [ ] 用户可见文案为中文业务语言，不含技术实现细节。
- [ ] 统计、标签页和列表使用同一状态与计数口径。
- [ ] 零结果、加载、错误、禁用和完成状态均有明确反馈。
- [ ] 长任务有进度，完成后能找到产物或下一步。
- [ ] 产品没有代替用户执行公司政策或 Concur 最终提交。

只有以上检查通过，产品交互变更才可视为完成。
