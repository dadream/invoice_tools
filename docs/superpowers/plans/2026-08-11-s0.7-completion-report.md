## 交付内容

### 后端（`src-tauri/src/commands/invoice.rs`，新建）

5 个 IPC 命令，均返回 `AppResult<T>`：

| 命令 | 作用 |
|------|------|
| `parse_invoice` | 按扩展名分派到 invoice-parse，返回结构化字段供确认 |
| `check_duplicate` | 全库按发票号查重，命中时回传所在批次名 |
| `add_invoice_to_batch` | 后端重新解析并入库（不信任前端回传字段） |
| `list_batch_invoices` | 列出批次下发票 |
| `delete_invoice` | 删除发票（仅 Draft 批次） |

3 个 DTO（`ParsedInvoiceDto` / `InvoiceDto` / `DuplicateCheckDto`），
金额与日期全部字符串化跨 IPC。

PDF 解析先走 L1 坐标路径（`parse_vat_invoice_from_boxes`），失败降级
flat-text，与 invoice-parse CLI 的 `pdf-vat` 分支一致。

### 数据库（`crates/invoice-store/src/ledger_db.rs`）

新增 `find_invoice_by_number`（跨批次查重）与 `get_invoice`（单条读取，
`delete_invoice` 的 Draft 校验需要）。两者均用 `optional()` 处理无行。

## 实现中发现并修正的问题

按发现顺序，均已修复并有测试覆盖。

### 1. 计划中的解析器签名错误（实现前修正）

草稿计划写的是 `invoice_parse::xml::parse_xml(&path)`，实际不存在。
真实签名接收**字节**且**票种是入参**：

```rust
parse_invoice_xml(bytes: &[u8], path: &Path, hints: &TagHints, ticket_type: TicketType)
```

### 2. 前端无法用 `File.path`（实现前修正）

草稿计划用 `input.files[0].path`，Tauri v2 webview 中该属性为 `undefined`。
改为引入 `tauri-plugin-dialog` 2.7.2（crate + npm 版本对齐），
路径经 `open()` 与 `onDragDropEvent` 获取。

### 3. hints 不是全局配置（实现前修正）

`fixtures/manifest.toml` 无全局 `[hints]` 段，hints 是逐样本的
`[sample.xml_tag_hints]`；且 `fixtures/` 不随应用分发。
改为在 `builtin_hints()` 内置样本标签并集。CLAUDE.md 原先记载的
全局 `[hints]` 示例是错的，已同步更正——这正是误导草稿计划的源头。

### 4. PDF 解析 panic 会杀死进程（实现中发现，实测复现）

计划原以为 `pdf_text.rs` 自带的 `catch_unwind` 足够。实际 flat-text 回落路径
`pdf::extract_text` **无防护**，而 `pdf-extract` 对某些字体编码直接
`assert!(name == "Identity-H")`。由于分派逻辑是「L1 失败才走 flat-text」，
未防护路径恰好在常见情况下被触发。样本 `06-unknown-fbf5dc58.pdf` 可复现，
验证过程被直接杀死。现已在命令层统一 `catch_unwind` 兜住，并加回归测试
（夹具缺失时跳过）。

### 5. `ParseError` 的 Display 泄露 PII（实现中确认）

四个变体全部泄露：`Io`/`MalformedFormat`/`MissingField` 带完整文件路径，
`UnparseableValue` 带 `raw`——即真实字段值（金额或发票号）。
统一经 `parse_error_message()` 只保留错误类别与字段**名**，
panic payload 整体丢弃。有测试断言路径、姓名、原始值均不残留。

### 6. S0.6 遗留的运行时 bug（顺带修复）

`#[tauri::command]` 默认把参数名重写为 camelCase
（`tauri-macros-2.6.3/src/command/wrapper.rs:51,507`），而 DTO 字段经 serde
保持 snake_case——两套大小写并存。S0.6 的 `BatchDetail.svelte` 传的是
`new_status`，后端期望 `newStatus`，**每次状态流转都会失败**
（`missing required key newStatus`）。类型检查抓不到这类错误。

已修复，并核查全部调用点：`transition_batch_status` 是唯一一处，
其余多词参数（`batchId`/`invoiceId`/`invoiceNumber`/`ticketType`）均正确。

### 7. DTO 命名约定统一（评审时修正）

Task 1 初版按草稿计划用了 camelCase DTO，与 S0.6 已有的 `Batch`
（`total_amount`、`invoice_count`）不一致。以既有约定为准，
统一改为 snake_case。

### 8. 顺带清理 a11y 警告

`CreateBatchModal.svelte` 的遮罩层缺键盘处理器（S0.6 遗留警告）。
改为只在点击遮罩自身时关闭，省掉内层 `stopPropagation`，
并补 `aria-modal` / `aria-labelledby`。check 现为 0 warnings。

## 已知限制

- **票种需用户手选**：解析器不推断票种。`invoice-collect/src/classify.rs`
  的分类逻辑面向邮件附件，未接入解析链路。自动推断留待后续。
- **GUI 手动验收阻塞**：WSL2 无 display server，无法启动窗口验收交互路径。
  逻辑由后端测试（invoice-assistant 31 + invoice-store 51）
  加 10 个前端测试与 CLI 等价验证覆盖。
  首次在有显示环境的机器上运行时，仍需人工确认拖拽与文件对话框行为。
- **内置 hints 覆盖面**：hints 来自现有样本聚合，新格式发票可能解析失败
  并回落到错误提示。扩展 hints 需同时改 manifest 与 `builtin_hints()`。
- **查重仅按发票号**：多字段校验与模糊查重属 G1 任务范围。
- **合计金额前端为展示值**：`sumAmounts()` 用于页脚展示，
  精确合计以后端 Decimal 为准。
