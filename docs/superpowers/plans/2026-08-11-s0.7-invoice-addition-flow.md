# S0.7 发票添加流程 Implementation Plan

**日期**: 2026-08-11
**任务**: S0.7 发票添加流程（选择文件 → 解析 → 确认 → 存入批次）
**前置**: S0.6 批次 CRUD UI（已完成，commit 746ac86）

## 目标

在 S0.6 的批次详情页上接入"添加发票"闭环：用户选择本地发票文件（XML/OFD/PDF），
后端调用 `invoice-parse` 解析出结构化字段，前端展示解析结果供确认，确认后写入
`ledger.db` 的 `reported_invoices` 表并挂到当前批次。

## 已验证的关键 API 事实（务必按此实现，不要凭记忆猜测）

以下签名均已在本仓库源码中核对过，实现时必须严格匹配：

### 1. 解析器签名（`crates/invoice-parse/src/`）

三个解析入口**都接收文件字节、而不是路径**，并且**票种是入参、解析器不会自行判定**：

```rust
// xml.rs:100
pub fn parse_invoice_xml(bytes: &[u8], path: &Path, hints: &TagHints, ticket_type: TicketType)
    -> Result<ParsedInvoice, ParseError>
// ofd.rs:76
pub fn parse_invoice_ofd(ofd_bytes: &[u8], path: &Path, hints: &TagHints, ticket_type: TicketType)
    -> Result<ParsedInvoice, ParseError>
// pdf.rs:9
pub fn parse_invoice_pdf(pdf_bytes: &[u8], path: &Path, _hints: &TagHints, ticket_type: TicketType)
    -> Result<ParsedInvoice, ParseError>
// pdf_text.rs:171 —— 增值税 PDF 的 L1 坐标路径，优先于 flat-text
pub fn parse_vat_invoice_from_boxes(pdf_bytes: &[u8], path: &Path)
    -> Result<ParsedInvoice, ParseError>
```

模块通过 `invoice_parse::xml::` / `::ofd::` / `::pdf::` / `::pdf_text::` 访问
（`lib.rs` 只导出模块，不做函数级 re-export）。

### 2. TagHints 必须在代码里构造，不能从 manifest 全局加载

`fixtures/manifest.toml` **没有全局 `[hints]` 段**，hints 是**逐样本**的
`[sample.xml_tag_hints]`。且 `fixtures/` 是开发夹具、不随应用分发，因此
应用内必须内置一份合并后的 hints 常量。已从全部样本聚合出并集：

```rust
invoice_number = ["InvoiceNumber", "EIid"]
issue_date     = ["IssueTime", "RequestTime"]
total_amount   = ["TotalTax-includedAmount"]
tax_amount     = ["TotalTaxAm"]
tax_rate       = ["TaxRate"]
buyer_name     = ["BuyerName"]
seller_name    = ["SellerName"]
```

`TagHints`（`manifest.rs:55`）7 个字段全为 `Vec<String>`，均带 `#[serde(default)]`。

### 3. 存在两个不同的 TicketType 枚举，必须显式互转

- `invoice_parse::model::TicketType` —— 解析输出用，`Serialize/Deserialize`，**无** `to_str`/`from_str`
- `invoice_store::models::TicketType` —— 数据库存储用，有 `to_str()`（`models.rs:218`，
  产出 `"rail"`/`"flight"`/`"hotel"`/`"city_transport"`/`"meal"`/`"other"`）
  与 `from_str()`（`models.rs:230`，返回 `Option<Self>`）

两者变体同名同序（Rail/Flight/Hotel/CityTransport/Meal/Other），但**是不同类型**，
不能直接赋值。必须写显式 `match` 映射函数。

### 4. 数据库方法现状（`crates/invoice-store/src/ledger_db.rs`）

- `add_invoice(&self, invoice: &ReportedInvoice) -> StoreResult<i64>` —— **已存在**（244 行）
- `list_invoices_by_batch(&self, batch_id: i64) -> StoreResult<Vec<ReportedInvoice>>` —— **已存在**（280 行）
- `delete_invoice(&self, id: i64) -> StoreResult<()>` —— **已存在**（296 行附近）
- `find_invoice_by_number(...)` —— **不存在，本任务需新增**

`ReportedInvoice`（`models.rs:147`）字段：`id, batch_id, invoice_number, issue_date,
amount(Decimal), tax_amount, buyer_name, seller_name, ticket_type, city,
departure_time, checkin_date, file_path, created_at, updated_at`。
注意金额字段名是 **`amount`**，不是 `total_amount`；且**没有 `tax_rate` 列**
（见表结构 `ledger_db.rs:56`），`confidence`/`parse_level` 同样没有列 —— 解析级别
只在确认阶段展示给用户，不入库。

### 5. 查不到记录时的错误形态（S0.5 已踩过的坑）

`rusqlite` 的 `query_row` 在无行时返回 `Error::QueryReturnedNoRows`，经
`#[from]` 落进 `StoreError::Database(_)`，**不是** `StoreError::NotFound`。
重复检查必须用 `optional()`（`rusqlite::OptionalExtension`）或显式匹配
`QueryReturnedNoRows`，绝不能靠匹配 `NotFound` 判断"不存在"。

### 6. 前端拿不到 `File.path`

Tauri v2 的 webview 中 `File` 对象**没有 `path` 属性**（那不是浏览器 API），
`input.files[0].path` 与 `dataTransfer.files[0].path` 都是 `undefined`。
要拿真实文件系统路径必须用 `@tauri-apps/plugin-dialog` 的 `open()`，
拖拽则用 `getCurrentWebview().onDragDropEvent()`（其 payload 提供 `paths`）。

已确认可安装（网络可达，无 cargo offline 锁定，`vendor/` 仅含 onnxruntime）：
- crate `tauri-plugin-dialog = "2.7.2"`
- npm `@tauri-apps/plugin-dialog@2.7.2`

版本对齐，且与现有 `plugin-shell` 2.3.1 的接入方式一致。

## Global Constraints

- **金额精度**：全程 `rust_decimal::Decimal`，跨 IPC 一律转字符串，禁止 f64
- **日期格式**：`NaiveDate` ↔ `"YYYY-MM-DD"` 字符串
- **PII**：日志与错误信息中不得出现发票号、金额、姓名、邮箱；只记录文件扩展名、
  解析级别、错误类别
- **panic containment**：PDF 解析可能 panic，`pdf_text.rs` 内部已有 `catch_unwind`，
  命令层仍需把 `ParseError` 映射为 `AppError::parse`，不得让 panic 逃逸到 IPC 边界
- **Svelte 5 runes**：`$state`/`$derived`/`$effect`/`$props`，禁止 Svelte 4 的
  `export let` 与 `new Component()`
- **构建前置**：任何 `invoice-assistant` 的 cargo 构建/测试前必须
  `source scripts/tauri-env.sh`
- **错误契约**：命令返回 `AppResult<T>`，错误经 `AppError::{parse,database,validation,io}`
  构造，保持 `{kind, message, recoverable}` 三字段
- **不改动既有通过的测试**：S0.6 的 208 个测试必须继续全绿

fn parse_level_to_string(level: ParseLevel) -> &'static str {

fn to_store_ticket_type(t: ParseTicketType) -> StoreTicketType {

        ParseTicketType::Hotel => StoreTicketType::Hotel,
        ParseTicketType::CityTransport => StoreTicketType::CityTransport,

### Step 4: parse_invoice 命令

按扩展名分派，读字节后调用对应解析器。PDF 先走 L1 坐标路径、失败再降级
flat-text（与 `invoice-parse/src/main.rs` 的 `pdf-vat` 分支一致）：

```rust
#[tauri::command]
pub fn parse_invoice(path: String, ticket_type: Option<String>)
    -> AppResult<ParsedInvoiceDto>
{
    let p = std::path::Path::new(&path);
    if !p.is_file() {
        return Err(AppError::validation("文件不存在或不是普通文件"));
    }
    let ext = p.extension()
        .and_then(|e| e.to_str())
        .map(|e| e.to_ascii_lowercase())
        .unwrap_or_default();

    let bytes = std::fs::read(p)
        .map_err(|e| AppError::io(format!("读取文件失败: {}", e.kind())))?;

    let hints = builtin_hints();
    let tt = ticket_type.as_deref().map(ticket_type_from_str)
        .unwrap_or(ParseTicketType::Other);

    let parsed = match ext.as_str() {
        "xml" => invoice_parse::xml::parse_invoice_xml(&bytes, p, &hints, tt),
        "ofd" => invoice_parse::ofd::parse_invoice_ofd(&bytes, p, &hints, tt),
        "pdf" => invoice_parse::pdf_text::parse_vat_invoice_from_boxes(&bytes, p)
            .or_else(|_| invoice_parse::pdf::parse_invoice_pdf(&bytes, p, &hints, tt)),
        other => return Err(AppError::validation(
            format!("不支持的文件类型: .{}", other))),
    };

    // 错误信息只带类别，不回显文件内容（PII 约束）
    let parsed = parsed.map_err(|e| AppError::parse(format!("解析失败: {}", e)))?;
    Ok(parsed.into())
}
```

注意 `AppError::io` 里只用 `e.kind()`，不拼接完整路径，避免把用户目录结构写进日志。
若 `ParseError` 的 Display 可能带字段值，则改为只映射错误变体名——实现时检查
`ParseError` 的 `#[error(...)]` 文案，含具体字段值的一律不外传。

### Step 6: add_invoice_to_batch 命令

签名只接 `batch_id`、`path`、`ticket_type`，**后端重新解析**而非信任前端传回的字段：

```rust
#[tauri::command]
pub fn add_invoice_to_batch(
    state: tauri::State<AppState>,
    batch_id: i64,
    path: String,
    ticket_type: Option<String>,
) -> AppResult<InvoiceDto>
```

顺序：
1. `get_batch(batch_id)` 确认批次存在，且状态为 `Draft`——非 Draft 批次禁止加票，
   返回 `AppError::validation("只有草稿状态的批次可以添加发票")`
2. 重新解析文件（复用 Step 4 的内部函数，抽一个不带 `#[tauri::command]` 的
   `fn do_parse(path, ticket_type) -> AppResult<ParsedInvoice>` 供两处共用）
3. 再查一次重复，命中则返回 `AppError::validation("该发票已报销")`（防 TOCTOU）
4. 构造 `ReportedInvoice`：`id: 0`（由 DB 自增填充）、`amount` 取
   `parsed.total_amount`、`ticket_type` 走 `to_store_ticket_type`、
   `file_path` 存绝对路径、`created_at`/`updated_at` 由 `add_invoice` 内部写
5. `add_invoice` 拿到 id 后回读并转 `InvoiceDto` 返回

`ReportedInvoice` 无 `tax_rate`/`parse_level`/`confidence` 字段，构造时不要写。

### Step 3: 文件选择封装

`ui/src/lib/invoice.ts` —— 把 dialog 与拖拽两条路径都收在这里，
组件只调用这一层：

```ts
import { open } from '@tauri-apps/plugin-dialog';
import { getCurrentWebview } from '@tauri-apps/api/webview';

export const SUPPORTED_EXTENSIONS = ['xml', 'ofd', 'pdf'];

/** 打开系统文件选择器，返回绝对路径；用户取消返回 null */
export async function pickInvoiceFile(): Promise<string | null> {
  const selected = await open({
    multiple: false,
    directory: false,
    filters: [{ name: '发票文件', extensions: SUPPORTED_EXTENSIONS }],
  });
  return typeof selected === 'string' ? selected : null;
}

/** 注册拖拽监听，回调收到的是绝对路径数组；返回 unlisten 函数 */
export async function onInvoiceDrop(
  handler: (paths: string[]) => void
): Promise<() => void> {
  const webview = getCurrentWebview();
  return await webview.onDragDropEvent((event) => {
    if (event.payload.type === 'drop') {
      const paths = event.payload.paths.filter((p) =>
        SUPPORTED_EXTENSIONS.includes(p.split('.').pop()?.toLowerCase() ?? '')
      );
      if (paths.length > 0) handler(paths);
    }
  });
}
```

组件里用 `$effect` 注册并在 cleanup 中调用 unlisten，避免重复监听。

## 已知限制

- **票种需用户选择**：解析器不推断票种（`invoice-collect/src/classify.rs`
  的分类逻辑面向邮件附件，未接入解析链路）。自动推断留到后续任务
- **GUI 手动验收阻塞**：WSL2 无 display server，交互路径靠单元测试与
  CLI 等价验证覆盖

  解析失败并回落到错误提示；扩展 hints 是后续增量工作
- **查重仅按发票号**：G1 任务的多字段校验/模糊查重不在本任务范围
- **合计金额前端为展示值**：精确合计以后端 Decimal 为准
