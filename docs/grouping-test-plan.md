# 归组引擎 α 测试计划

## 目标

验收线：**平均调整 < 3 张/批次**（等价于准确率 ≥ 94%）

### 目标用户画像

- 已使用报销系统（如 Concur）≥ 6 个月
- 月均发票量 ≥ 15 张
- 经常出差（至少包含 2-3 次多日行程）
- 理解"行程"概念，能够准确判断分组是否合理

### 测试规模

- **用户数量**: 5 人
- **批次数量**: 每人 3-5 个历史月份 = 15-25 个批次
- **总发票量**: 预计 300-500 张

---

## 测试方法

### 准备阶段

1. **招募 α 用户**
   - 发布招募通知（内部邮件/技术社区）
   - 筛选条件：符合目标用户画像
   - 确认数据隐私协议（不上传发票图片，仅处理本地解析结果）

2. **收集历史数据**
   - 每位用户提供 3-5 个历史月份的发票文件
   - 文件格式：XML/OFD/PDF（与解析器兼容）
   - 同时提供用户原始分组记录（如 Excel 报销单）

3. **环境准备**
   - 使用试运行模式（不计费、不写台账）
   - 准备数据收集表格模板
   - 安装工装脚本（见"工装需求"章节）

### 执行阶段

对每个批次执行以下流程：

1. **解析发票**
   ```bash
   cargo run -p invoice-parse -- batch <files> -o parsed.json
   ```
   输出：`Vec<ParsedInvoice>` JSON 文件

2. **运行归组引擎**
   ```bash
   cargo run -p invoice-grouping -- group parsed.json -o grouped.json
   ```
   输出：分组结果（每组包含发票列表、歧义标记）

3. **审核分组结果**
   - 与用户一起逐批次查看归组结果
   - 对比用户原始分组记录
   - 识别需要调整的发票（移动、拆分、合并、排除）

4. **记录调整数据**
   - 使用数据收集表格记录每次调整
   - 记录调整类型和原因
   - 统计每个批次的调整张数

### 数据收集表格

| 批次ID | 用户 | 月份 | 总张数 | 调整张数 | 调整类型分布 | 备注 |
|--------|------|------|--------|----------|--------------|------|
| B01 | U1 | 2026-06 | 48 | 2 | 移动2 | 周末判断错误（周六凌晨误判为上一行程） |
| B02 | U1 | 2026-07 | 52 | 1 | 拆分1 | 连续3天出差中间回家1天未识别 |
| B03 | U2 | 2026-06 | 35 | 4 | 移动3, 排除1 | 移动：同城多地点误判；排除：发票日期错误 |
| ... | ... | ... | ... | ... | ... | ... |

**字段说明**:
- **批次ID**: 唯一标识符（B01, B02, ...）
- **用户**: 匿名化标识（U1, U2, ...）
- **月份**: 发票所属月份（YYYY-MM）
- **总张数**: 批次中发票总数
- **调整张数**: 需要手工调整的发票数量
- **调整类型分布**: 移动/拆分/合并/排除的次数
- **备注**: 调整原因和问题描述

## 分析标准

### 达标条件

系统通过 α 测试需要同时满足：

1. **量化指标**: 平均调整张数 < 3
   - 计算公式：`总调整张数 / 批次数量`
   - 示例：50 次调整 / 20 个批次 = 2.5 张/批次 ✅ 达标

2. **质量指标**: 无系统性错误
   - 定义：同一类型错误占比 > 30% 视为系统性错误
   - 示例：60 次调整中有 25 次是"周末夹中间"误判（41.7%）→ 未达标

### 未达标处理流程

根据错误分布类型选择迭代策略：

#### 情况1：调整集中在少数几类（系统性错误）

**特征**: 
- Top 3 调整类型占比 > 60%
- 同一问题重复出现在多个批次

**处理策略**:
- 分析根因（算法漏洞 vs 规则缺失）
- 补充规则或修复算法逻辑
- 重新测试受影响的批次
- 预计迭代周期：1-2 周

**示例**:
```
调整分布：周末夹中间误判 45%，同城多地点误判 30%，其他 25%
→ 优先修复周末判断逻辑和地点相似度算法
```

#### 情况2：调整分散在各类型（算法框架问题）

**特征**:
- 调整类型分布均匀（无明显主导类型）
- 每个错误场景差异很大

**处理策略**:
- 重新评估算法框架设计
- 考虑增加更多上下文信息（如地点、出行方式）
- 可能需要重构核心算法
- 预计迭代周期：2-4 周

#### 情况3：两次迭代无改善

**处理策略**:
- 重新评估归组作为 MVP 核心能力的可行性
- 考虑降级方案：
  - 提供半自动归组（系统建议，用户确认）
  - 降低归组精度要求，增加手工调整空间
  - 延后归组功能到 v2.0

### 系统性错误识别指南

**判断依据**:
1. 统计各调整类型的频次
2. 计算每类占总调整的百分比
3. 如果 Top 1 类型 > 30%，标记为系统性错误

**常见系统性错误类型**:
- 周末时间判断错误（周六凌晨、周日夜晚）
- 同城多地点误判为同一行程
- 连续多天中间回家1天未识别
- 票据类型判断错误（市内交通 vs 外地交通）

## 工装需求

为支持 α 测试流程，需要开发以下辅助工具：

### 1. 批量导入历史批次工具

**功能**: 
- 批量解析用户提供的发票文件
- 自动生成 `parsed.json` 文件
- 支持增量导入（避免重复解析）

**命令示例**:
```bash
cargo run -p invoice-parse -- batch-import \
  --input-dir fixtures/alpha/user1/202607 \
  --output parsed_user1_202607.json
```

### 2. 归组调整统计脚本

**功能**:
- 对比系统分组结果与用户手工调整后的分组
- 自动计算调整张数和类型分布
- 输出统计报告（支持导出为表格）

**命令示例**:
```bash
cargo run -p invoice-grouping -- diff \
  --system-grouped grouped.json \
  --user-adjusted user_adjusted.json \
  --output adjustment_stats.csv
```

### 3. 可视化对比工具

**功能**:
- 并排展示系统分组 vs 用户期望分组
- 高亮差异点（需要调整的发票）
- 支持时间轴视图（方便识别时间判断错误）

**技术选型**:
- 后端：Rust 生成 HTML 报告
- 前端：简单的静态 HTML + CSS（无需复杂框架）
- 数据格式：JSON 嵌入 HTML

**输出示例**:
```bash
cargo run -p invoice-grouping -- visualize \
  --grouped grouped.json \
  --output report.html
```

### 4. 数据收集表格生成器

**功能**:
- 从调整统计结果自动生成表格行
- 减少手工填写工作量
- 支持合并多个批次的统计结果

**命令示例**:
```bash
cargo run -p invoice-grouping -- generate-table \
  --stats-dir fixtures/alpha/stats \
  --output alpha_test_results.md
```
